# release-auto

Точка входа для еженедельной cloud-routine. Сам ничего не публикует: делает
предполётные проверки и, если все сошлись, запускает
[`release`](../release/SKILL.md) с `UNATTENDED=true`.

Смысл разделения: `release` умеет выпускать, `release-auto` решает, **можно
ли выпускать сегодня**. Все решения принимаются до первой необратимой
операции — после запуска `release` откатить публикацию уже нельзя.

## Когда запускать

Из routine по расписанию — **по пятницам в 13:00**. Вокруг этого времени
человек держит `main` замороженным: с 12:00 (перед перелитием) и до отчёта
routine, ориентировочно 14:00.

Вручную имеет смысл запустить, чтобы проверить готовность веток, не выпуская
релиз, — но тогда останови процесс после отчёта предполёта.

Для ручного релиза с известной версией используй `release` напрямую.

**Пропустить неделю** — задача человека: он отключает routine в расписании.
Отдельного признака «на этой неделе не релизим» в репозитории нет и заводить
его не надо.

## Что должно быть сделано человеком

Регламент подготовки — [`docs/human/release.md`](../../../docs/human/release.md).
Кратко, в порядке выполнения:

1. Все задачи спринта смержены в `main`, дальше `main` заморожен до релиза.
2. `stories/release-notes/v1/<VERSION>.mdx` заполнен — он же признак того,
   что релизить есть что.
3. `main` перелит в `release-0`, конфликты React 17-адаптаций разрешены,
   ветка запушена, CI на ней зелёный.

Порядок 1 → 3 обязателен: коммит, попавший в `main` после перелития, уронит
проверку `is-ancestor`, и релиза не будет. Поэтому перелитие — последнее, что
происходит с `main` перед релизом, а сама `main` заморожена до отчёта.

Если предполёт упал из-за нарушенной заморозки, чинить это самому нельзя:
доливать `main` в `release-0` — ручной шаг, его результат должен пройти CI.
Скажи в отчёте, каких коммитов не хватает, и остановись.

## 1. Версия и есть ли что релизить

```bash
git fetch origin --prune
git show origin/main:package.json | grep -m1 '"version"'
```

`VERSION` = минор из `origin/main` + 1, патч `0`. Версия `1.40.0` в `main`
означает, что выпускается `1.41.0`. Из `VERSION` выводятся `V0` = `0.Y.0`,
`NEXT` = `1.(Y+1).0`, `NEXT0` = `0.(Y+1).0`.

Признак того, что релизить есть что, — **заполненные release notes на эту
версию**:

```bash
git show origin/main:stories/release-notes/v1/<VERSION>.mdx
```

Файл существует практически всегда: заготовку на `VERSION` создаёт
предыдущий релиз, а пункты в неё дописываются по ходу спринта. Значение
имеет не наличие файла, а его содержимое — по **предикату заготовки**
([`release-react18`](../release-react18/SKILL.md), шаг 1):

- **Заготовка** (кроме шапки и пустых `<Heading>` ничего нет) → штатный
  выход. Это не ошибка: с прошлого релиза в библиотеку ничего не приехало,
  выпускать нечего. Отчёт в одну строку, дальше не идти.
- **Заполнен** → продолжаем предполёт.
- **Файла нет вообще** → стоп. Предыдущий релиз не создал заготовку, это
  аномалия, а не «нечего релизить».

Читай файл именно из `origin/main` (`git show`), а не из рабочей копии:
чекаут routine может стоять на произвольной ветке.

## 2. Предполётные проверки

Любая не сошлась — стоп с отчётом. Ничего не публикуется, ничего не чинится
молча: каждая из этих проверок означает, что подготовка не завершена, а
достраивать её за человека нельзя.

```bash
git status --porcelain
git show origin/release-0:package.json | grep -m1 '"version"'  # версия release-0
gh release view <VERSION> 2>&1 | head -3
gh release view <V0> 2>&1 | head -3
git rev-parse origin/main
git merge-base --is-ancestor origin/main origin/release-0
gh run list --workflow=ci.yml --branch release-0 --limit 1 \
  --json headSha,status,conclusion,url
git rev-parse origin/release-0
```

| Проверка | Условие |
|---|---|
| Рабочее дерево | чистое |
| Релизы | ни `VERSION`, ни `V0` ещё не выпущены |
| Миноры веток | минор в `main` и в `release-0` совпадает |
| Перелитие | `is-ancestor origin/main origin/release-0` проходит |
| CI `release-0` | последний прогон `ci.yml` на `release-0`: `headSha` = вершина `origin/release-0`, `status` = `completed`, `conclusion` = `success` |

Версия и release notes проверены на шаге 1 — здесь не повторяются.

При провале `is-ancestor` покажи, чего именно не хватает, — иначе сообщение
бесполезно:

```bash
git log origin/main --not origin/release-0 --oneline
```

Прогон CI на другом коммите, чем вершина ветки, **не считается зелёным**:
проверялось не то состояние `release-0`.

**Режим публикации.** До первого коммита определи, сможет ли этот прогон
публиковать, — безопасным зондом (диспатч на несуществующий ref не может
ничего запустить):

```bash
gh api -i --method POST \
  "repos/{owner}/{repo}/actions/workflows/release.yml/dispatches" \
  -f ref=__preflight_probe__ 2>&1 | head -3
```

- `422 No ref found` — право на диспатч есть, полный релиз возможен
  (локальный запуск с PAT).
- `403` — публикация из этой сессии запрещена (штатно для облака: прокси
  блокирует все пути публикации релиза — TRI-117; нерелизные workflow
  при этом диспатчатся). Это **не стоп**: продолжай,
  но с первой строки отчёта предупреди, что прогон только готовит релиз,
  а публикацию завершает человек по командам из отчёта. Подготовка
  оставляет `release-0` с бампнутой версией — пока человек не выпустит
  `0.Y.0`, следующий предполёт упадёт на проверке миноров; это ожидаемо
  и чинится доведением релиза, а не откатом.

Проверки выше — предполётные, чтобы не начинать релиз с заведомо неготовой
`release-0`. Повтор `is-ancestor` внутри `release` безвреден и ожидаем: обе
половины идут до того, как релизный PR добавит в `main` коммит с бампом,
поэтому сверяться можно прямо с вершиной `origin/main`.

## 3. Задача Linear

`TASK` — номер задачи Linear на релиз, формат `TRI-XXX`. Найди открытую
задачу «Релиз <VERSION> / <V0>»; если её нет — заведи через skill
`create-task`.

Linear MCP в headless-запуске может быть недоступен. Тогда **не** выдумывай
номер и не подставляй legacy-префикс: сообщи об этом в отчёте и остановись —
без `TASK` релизные коммиты не соответствуют
[`docs/ai/commits.md`](../../../docs/ai/commits.md).

## 4. Запуск релиза

Запусти [`release`](../release/SKILL.md), передав:

| Вход | Значение |
|---|---|
| `VERSION`, `V0`, `NEXT`, `NEXT0` | выведены на шаге 1 |
| `TASK` | из шага 3 |
| `UNATTENDED` | `true` |

Дальше всё ведёт `release`: React 17-половина (`0.Y.0`), гейт на её
успешность, React 18-половина (`1.Y.0`). Вмешиваться в его шаги не нужно — при остановке под-скила
просто передай его отчёт дальше.

## 5. Отчёт

Один итоговый отчёт в любом исходе. Обязательно должно быть видно, **что
именно произошло**, без чтения логов:

- **Релиза не было** — какая проверка не сошлась и что нужно доделать.
  Пустую заготовку notes формулируй как штатный пропуск («выпускать нечего»),
  а не как ошибку. Всё остальное — именно ошибка подготовки: пропуск недели
  делается отключением routine, а не незавершённой подготовкой, поэтому
  недоделанное перелитие или красный CI надо называть своим именем.
- **Релиз выпущен** — то, что вернул `release`: обе версии, ссылки на PR и
  GitHub Release, подтверждение `dist-tags.latest` = `VERSION`, каким путём
  пошли release notes React 17-половины, наличие ассета
  `mcp-data-<VERSION>.json`, ссылки на Storybook. Тег `react17` не упоминай —
  он не поддерживается.
- **Релиз подготовлен, публикация за человеком** — штатный исход облачного
  прогона (зонд режима публикации дал 403). Первой строкой: что именно
  подготовлено (`release-0` на `<V0>`, CI), затем готовая команда публикации
  `0.Y.0` из отчёта `release-react17` и напоминание продолжить React
  18-половину локально. `latest` не тронут, аварии нет — но релиз надо
  довести: до публикации `0.Y.0` следующий предполёт упадёт на минорах.
- **Вышла только `0.Y.0`** — это **авария**, а не «половина релиза». `latest`
  остался на React 17-сборке, и `npm install` отдаёт её всем потребителям.
  Ставь это первой строкой отчёта, называй аварией и указывай починку:
  довыпустить `1.Y.0` через `release-react18` либо вернуть тег вручную
  (`npm dist-tag add ...@<предыдущая 1.x> latest`). Сам тег не трогай.

## Жёсткие ограничения

- Не выпускать релиз при любой не сошедшейся предполётной проверке.
- Не доливать `main` в `release-0` и не чинить красный CI — подготовка веток
  целиком на человеке.
- Не перепроверять `is-ancestor` после мержа релизного PR в `main`.
- Не дописывать release notes, чтобы «было что релизить»: пустая заготовка —
  это ответ «выпускать нечего», а не проблема, которую надо решить.
- Не трогать `dist-tags` руками ни при каком исходе — только сообщать.
- Не выдумывать номер задачи Linear, если MCP недоступен.
