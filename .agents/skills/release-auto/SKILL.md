# release-auto

Отчётный skill для еженедельной cloud-routine. **Ничего не публикует и не пишет
в GitHub** — только читает результат и рассказывает о нём человеку.

Сам релиз делает [`release-weekly.yml`](../../../.github/workflows/release-weekly.yml)
по расписанию GitHub (пятница 13:23 МСК). Routine запускается после него.

## Почему релиз не здесь

Прокси облачных сессий режет write-пути `api.github.com`: `gh release create`,
`gh workflow run`, создание и push тегов — всё возвращает
`Write access to this GitHub API path is not permitted through this proxy`.
Три прогона подряд (TRI-113, TRI-116, TRI-118) упирались в это на разных шагах.

Изнутри Actions ограничений нет, поэтому механика живёт там, а расписание
держит сам GitHub. Не пытайся выпускать релиз отсюда — не получится, и это
не баг окружения, а его устройство.

## Что делать

### 1. Найти прогон

```bash
gh run list --workflow=release-weekly.yml --event=schedule \
  --created ">=<СЕГОДНЯ>" --limit 1 \
  --json databaseId,status,conclusion,createdAt,url
```

`<СЕГОДНЯ>` — текущая дата по МСК в формате `YYYY-MM-DD`; подставь её сам,
не вычисляй через `date` (у раннера свой часовой пояс). Прогон стартует
в пятницу 13:23 МСК, routine идёт следом в тот же день.

Оба фильтра обязательны, каждый закрывает свою ошибку:

- `--event=schedule` — иначе поймаешь посторонний ручной прогон, в частности
  `dry_run`, у которого `preflight` успешен, а остальные джобы `skipped`.
  Выглядит один в один как «релиза не было штатно». Нужный ручной прогон
  ищется отдельно и по своим правилам — шаг 1а;
- `--created` — иначе `--limit 1` вернёт самый свежий scheduled run
  **любого возраста**, и отчёт соберётся по прошлонедельному релизу.

Сверь `createdAt` в выводе с сегодняшней датой ещё раз, прежде чем читать
исход: это дешевле, чем неверный отчёт в Linear.

### 1а. Проверить ручной прогон

Расписание опаздывает — это регулярный, а не аварийный случай: 28.08 плановый
прогон пришёл на 11 часов позже времени, 04.09 — на 4 (TRI-138). По
`docs/human/release.md` человек в таком случае должен запустить релиз
вручную в 13:45 — но мог и не успеть. Отсюда два вида обманчивой картины:

- **scheduled-прогона нет** — список выше пуст;
- **scheduled-прогон есть, но пустой** — опоздал, пришёл уже после ручного
  релиза и штатно вышел с «пустая заготовка notes»: версия к тому моменту
  забамплена, кандидатом стала следующая. По джобам это неотличимо от
  «релиза не было штатно».

Оба раза релиз на самом деле выпущен. Поэтому **прежде чем отчитаться
«релиза не было» — хоть по пустому списку, хоть по отказу предполёта —
проверь ручные прогоны за тот же день**:

```bash
gh run list --workflow=release-weekly.yml --event=workflow_dispatch \
  --created ">=<СЕГОДНЯ>" --limit 10 \
  --json databaseId,status,conclusion,createdAt,url
```

Их за день бывает несколько (28.08 — четыре: неудачные попытки подготовки
и финальная). Отбирай в два приёма.

**Сначала по `status` из списка.** Прогон `in_progress` или `queued` — не
кандидат на отбраковку, а повод подождать: запуск в 13:45 плюс ~9 минут
прогона приходятся впритык к твоему времени. Дождись завершения и только
потом разбирай — иначе джоба публикации ещё нет и любой отбор по джобам
даст пустоту, неотличимую от «кандидата нет».

**Затем по джобам.** Нужен последний прогон, в котором **публикация вообще
началась** — то есть джоб с префиксом `publish-react17` не `skipped`
(у reusable workflow имя `publish-react17 / build-and-publish`, а голое
`publish-react17` бывает только у пропущенного):

```bash
gh run view <RUN_ID> --json jobs \
  --jq '[.jobs[] | select(.name | startswith("publish-react17"))] | .[0].conclusion'
```

Критерий именно «публикация началась», а не «React 18 опубликована»: если
`0.Y.0` вышла, а `1.Y.0` упала — это авария, `dist-tags.latest` стоит на
React 17-сборке и об этом нужно кричать громче всего. Отбор по успеху
React 18 такой прогон отбросил бы, и отчёт получился бы «релиза не было»
в самой опасной из возможных ситуаций.

`conclusion` самого прогона для отбора не годится — он `success` и у отказа
предполёта.

Нашёлся — по нему и собирай отчёт (шаг 2), отдельно отметив, что прогон был
ручной, а расписание опоздало. Что именно случилось — полный релиз или
авария — разложит таблица исходов шага 2, здесь это не решай.

Ни одного такого нет — релиза на этой неделе пока не было. Не спеши
называть это поломкой: по опыту выше плановый прогон приходит и через
четыре часа, и через одиннадцать, так что к 14:00 самый вероятный вариант —
что он ещё в очереди, а человек не сделал страховочный запуск. Так и
напиши: релиза нет, прогон, возможно, ещё придёт, стоит проверить Actions
позже. Сам релиз не выпускай: из облака это не работает (см. выше).
Отчёт по вчерашнему прогону не годится.

Отдельно про `dry_run`: у такого прогона джобы выглядят как у отказа
предполёта. Различает их причина отказа из шага 2 — при `dry_run` её нет.

### 2. Определить исход

```bash
gh run view <RUN_ID> --json jobs \
  --jq '.jobs[] | "\(.name): \(.status)/\(.conclusion)"'
```

| Что видно | Исход |
|---|---|
| `preflight` успешен, остальные `skipped` | Релиза не было штатно — подготовка не завершена или выпускать нечего |
| Все джобы успешны | Релиз выпущен целиком |
| `publish-react17` успешен, дальше провал | **Авария** — см. ниже |
| `preflight` провалился | Поломка самого workflow |

Причину штатного пропуска бери из лога предполёта — там она написана
словами. `grep -v echo` обязателен: Actions печатает в лог и сам текст
скрипта, поэтому без него первым делом поймаешь определение `fail()`
с неподставленным `$1` вместо настоящей причины.

```bash
gh run view <RUN_ID> --log | grep -a "⏭️ Релиза не будет:" | grep -av echo
```

Пусто при успешном `preflight` — значит предполёт прошёл, и это `dry_run`,
а не штатный пропуск. Пусто при провалившемся `preflight` — падение мимо
`fail()`, причину ищи в конце лога.

### 3. Сверить состояние

```bash
git fetch origin main release-0
git show origin/main:package.json | grep -m1 '"version"'
git show origin/release-0:package.json | grep -m1 '"version"'
npm view @sberbusiness/triplex-next dist-tags --json
gh release view <VERSION> --json assets --jq '.assets[].name'
```

Ожидается: миноры веток совпадают, `dist-tags.latest` = `1.Y.0`, в релизе
`1.Y.0` лежат `dist-<VERSION>.zip` и `mcp-data-<VERSION>.json`.

`dist-tags.react17` **не проверяй** — тег не поддерживается, теги во внутренний
registry не проносятся.

### 4. Отчёт в Linear

**Это единственная связь релиза с трекером.** Релизные коммиты делает GitHub
Actions без префикса `TRI-XXX` — у workflow нет доступа к Linear, и номер
взять неоткуда (исключение зафиксировано в
[`docs/ai/commits.md`](../../../docs/ai/commits.md) § «Формат коммитов»).
Задачу заводишь ты, постфактум.

Найди задачу «Релиз `1.Y.0` / `0.Y.0`» через Linear MCP; если её нет, а релиз
состоялся — заведи через skill `create-task`. Опубликуй комментарий: что
выпущено, ссылки на релизы и коммиты, подтверждение `dist-tags.latest`,
ссылки на Storybook, наличие ассета для MCP-сервера.

Если релиза не было штатно — задачу не заводи, достаточно финального ответа
в сессии.

## Аномалии — называй первой строкой

**`latest` на `0.x`.** Значит `0.Y.0` опубликована, а `1.Y.0` нет, и
`npm install @sberbusiness/triplex-next` отдаёт всем React 17-сборку. Это
авария, а не «половина релиза». Почини её нельзя из облака — сообщи и дай
человеку команду:

```bash
npm dist-tag add @sberbusiness/triplex-next@<последняя 1.x> latest \
  --@sberbusiness:registry=https://registry.npmjs.org/ \
  --registry=https://registry.npmjs.org/
```

Оба флага обязательны: пакет лежит в `registry.npmjs.org`, а локальный
`@sberbusiness:registry` смотрит во внутренний registry и перебивает
одиночный `--registry`.

Либо довыпустить `1.Y.0` — тогда `latest` встанет сам.

**Релиз `1.Y.0` без `mcp-data-<VERSION>.json`.** MCP-сервер не сможет
синхронизироваться своим `sync-bundle.yml`. Сообщи, шаг `Generate MCP bundle`
не отработал.

**Прогон упал после публикации.** Версия в npm уже есть и отозвать её нельзя.
Скажи, что именно опубликовано, и что прогон можно перезапустить — публикация
идемпотентна.

## Жёсткие ограничения

- Ничего не публиковать и не пушить: релиз делает GitHub Actions.
- Не трогать `dist-tags` — только сообщать.
- Не заводить задачу Linear, если релиза не было.
- Не выдумывать причину пропуска: она написана в логе предполёта (шаг 2).
