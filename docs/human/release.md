# Подготовка и выпуск релиза — гайд для разработчика

Этот документ — для людей. Он описывает, что нужно сделать с ветками `main`
и `release-0`, чтобы релиз выпустился сам по расписанию, и что делать,
когда она отказалась.

Машинные инструкции, по которым работает агент, живут в `.agents/skills/`
(`release-auto`, `release`, `release-react18`, `release-react17`) — этот файл
их не заменяет, а показывает процесс сверху.

---

## Как устроен релиз

Библиотека выпускается парами версий:

| Версия | Ветка | React | Порядок выпуска |
|---|---|---|---|
| `0.Y.0` | `release-0` | 17 | первая |
| `1.Y.0` | `main` | 18 | вторая |

`0.Y.0` — функциональный аналог `1.Y.0` с React 17-адаптациями. Минор у них
всегда общий.

**Порядок обратен номерам версий, и это важно.** Теги не проносятся во
внутренний npm registry: `--tag` при публикации игнорируется, и
`dist-tags.latest` всегда встаёт на последнюю опубликованную версию. Поэтому
`1.Y.0` выпускается второй — только так `latest` остаётся на React 18-сборке,
и `npm install @sberbusiness/triplex-next` отдаёт именно её.

Отдельного тега для React 17 нет: `react17` в реестре не обновляется, ставить
на него не нужно. React 17-версия ставится по точному номеру.

Публикацию в npm делает GitHub Actions (`release.yml`). Ни у кого локально
npm-токена нет и не нужно. Запускается он тремя способами:

- **по расписанию** — `release-weekly.yml` вызывает его дважды, для `0.Y.0`
  и `1.Y.0`. Это основной путь, ничьего участия не требует;
- **вручную человеком** — создаёшь GitHub Release, workflow срабатывает по
  событию `release: published`. Текст notes из MDX собирает
  `node scripts/releaseNotesMd.js <файл.mdx>`;
- **локальным агентом** — skill `release` делает то же самое пошагово.

Из облачной сессии Claude — **никак**: прокси запрещает и создание релизов,
и запуск workflow, и push тегов. Поэтому расписание держит сам GitHub, а не
routine.

Все пути ведут к одному и тому же: сборка, публикация, ассеты, деплой
Storybook. Обратная сторона: **опубликованную версию нельзя отозвать**,
поэтому все проверки стоят до этого момента.

### Что настроено один раз

Автоматический путь опирается на две настройки репозитория. Если релиз
внезапно останавливается после предполёта или перед публикацией — проверь
в первую очередь их.

| Настройка | Где | Зачем |
|---|---|---|
| Секрет `RELEASE_TOKEN` | Settings → Secrets and variables → Actions | PAT `dudim-ai` (`contents: write`, `pull-requests: write`) — под ним workflow пушит бамп версии |
| `dudim-ai` в push restrictions и в bypass required pull requests | Settings → Branches → правило для `main` | иначе прямой push бампа в защищённый `main` не пройдёт |

`github-actions[bot]` в эти списки добавить нельзя — пикер показывает только
людей, команды и установленные GitHub Apps. Поэтому и нужен PAT машинного
аккаунта.

После любых изменений в этих настройках прогоняй **Actions → Weekly release
→ Run workflow** с галкой `dry_run`: выполнится только предполёт, ничего не
опубликуется.

## Кто что делает

Релиз целиком выпускает **GitHub Actions** — workflow
`release-weekly.yml` по расписанию GitHub. Claude в выпуске не участвует:
из облачной сессии релиз не выпустить, прокси режет создание релизов, push
тегов и запуск workflow. За ним остался отчёт.

| Когда | Кто | Что |
|---|---|---|
| весь спринт | **человек** | пункты в `stories/release-notes/v1/<VERSION>.mdx` |
| пт до 12:00 | **человек** | домержить задачи в `main`, дальше заморозка |
| пт ~12:00 | **человек** | перелитие `main` → `release-0`, конфликты, push |
| сразу после | GitHub | `ci.yml` на push в `release-0` |
| пт 13:00 | GitHub | `release-weekly.yml`: предполёт → `0.Y.0` → `1.Y.0` |
| пт ~14:00 | Claude | резюме в Linear, отметка аномалий |

Твоя часть — три пункта сверху, и по-настоящему ручной там один: перелитие.
Notes пишутся по ходу спринта, заморозка — это просто «не мержить».

### Откуда GitHub знает, что релизить

Версию берёт из `main`: минор в `package.json` + 1. Стоит `1.43.0` — значит
выпускается `1.44.0`.

Признак «есть что релизить» — **заполненные release notes на эту версию**,
`stories/release-notes/v1/1.44.0.mdx`. Файл существует всегда: заготовку
создаёт предыдущий релиз, а пункты в неё дописываются по ходу спринта.
Смотрит workflow не на наличие файла, а на содержимое:

- только шапка (`import`, `<Meta>`, `<Title>`, пустые `<Heading>`) — выпускать
  нечего, прогон штатно выходит;
- есть хоть один пункт — релизим.

Отдельного переключателя «в эту пятницу не релизим» нет. Чтобы пропустить
неделю с непустыми notes — отключи workflow в Actions или не делай перелитие
(тогда предполёт откажет, но напишет об этом как об ошибке подготовки).

## Расписание и заморозка `main`

Прогон стартует **по пятницам в 13:00 МСК**. Вокруг него окно заморозки:

```text
12:00  начало заморозки: в main больше ничего не мержим
       ├─ перелитие main → release-0, конфликты, push
       └─ зелёный CI на release-0
13:00  release-weekly.yml: предполёт → 0.Y.0 → 1.Y.0
~14:00 прогон завершён — заморозка снята
```

Два уточнения, без которых окно не работает:

**Заморозка начинается не по часам, а до перелития.** 12:00 — плановая
граница, при которой перелитие делается после неё. Начнёшь мерж в 12:05,
а в 12:30 кто-то вольёт PR в `main` — предполёт откажет: `release-0` уже
не содержит вершину `main`. Правило простое: **перелитие всегда последнее,
что происходит с `main` перед релизом.**

**Заморозка снимается по завершении прогона, а не в 14:00.** Час — оценка,
не гарантия: внутри установка зависимостей, unit-тесты, сборка, две
публикации в npm и деплой Storybook. Коммит, попавший в `main` до создания
релиза `1.Y.0`, уедет в него, но не в `0.Y.0` — версии разъедутся, а
`0.Y.0` должна быть точным аналогом.

Если релиз на этой неделе не планируется, заморозка не нужна вовсе.


## Чек-лист подготовки

Порядок важен. Пункт 3 выполняется **после** пунктов 1 и 2: коммит, попавший
в `main` после перелития, уронит проверку — и релиза не будет. Это касается
и правки release notes: она тоже коммит в `main`.

### `main`

**1. Смержить все задачи спринта.** Крайний срок — 12:00 пятницы, дальше
`main` заморожен до конца прогона. Заморозка не формальность: `release-0`
перелита из конкретного состояния `main`, и любой новый коммит делает её
устаревшей.

**2. Проверить release notes.** Файл `stories/release-notes/v1/<VERSION>.mdx`
должен быть заполнен — это шапка плюс реальные пункты:

```mdx
import { Meta, Title, Heading } from "@storybook/addon-docs/blocks";

<Meta title="release-notes/v1/1.44.0" />

<Title>v1.44.0</Title>

<Heading>Изменения</Heading>

- Badge: добавлена тема DANGER
```

Файл заводится заготовкой на предыдущем релизе, и пункты в него добавляются
по ходу спринта — обычно к пятнице он уже заполнен и делать ничего не нужно.
Голая шапка без пунктов = выпускать нечего, прогон штатно пропустит неделю.

Отдельного действия «объявить релиз» нет: заполненные notes и есть это
объявление.

### `release-0`

**3. Перелить `main`:**

```bash
git checkout release-0 && git pull origin release-0
git merge origin/main
```

**4. Разрешить конфликты.** Общий принцип: из `main` берётся логика и
поведение, из `release-0` сохраняется React 17-совместимость.

| Что | Откуда брать |
|---|---|
| React-зависимости в `package.json` | всегда из `release-0` (`react` 17.0.2, `@testing-library/react` 12.1.5 и т.д.) |
| Остальное в `package.json` | из `main` |
| `package-lock.json` | любая сторона, затем `npm install` |
| `.github/workflows/release.yml` | из `main` |
| `stories/release-notes/v0/*` | из `release-0` |
| `src/**` | логика из `main`, типовые адаптации из `release-0` |

Полная карта известных расхождений (полиморфные типы, `React.JSX`, `Portal`,
тесты) — в `.agents/skills/release-react17/SKILL.md`, раздел «Что делает
человек до релиза». Там же — grep-проверка на React 18-only API
(`useId`, `createRoot`, `react-dom/client` и прочее), которую стоит прогнать
после разрешения конфликтов.

**5. (Опционально) Release notes для React 17.** По умолчанию workflow
переносит текст `v1/1.44.0.mdx` → `v0/0.44.0.mdx` сам, меняя только
заголовки. Если какой-то пункт для React 17-сборки звучит иначе — заполни
`v0/0.44.0.mdx` руками и закоммить в `release-0`: заполненный файл workflow
не трогает.

Делай это **до** пуша, а не после. Routine проверяет, что зелёный прогон CI
стоит ровно на вершине `release-0`; коммит, добавленный после прогона,
сдвинет вершину, и проверка откажет. Если всё-таки закоммитил позже —
запушь и дождись нового прогона.

**6. Запушить и дождаться зелёного CI.** `ci.yml` запускается на push
в `release-0` — именно этот прогон проверяет предполёт. Красный CI
чиним до релиза.

Что покрывает этот прогон: сборка библиотеки, проверка циклических
зависимостей, unit-тесты, e2e. Чего он **не** покрывает: visual regression —
`visual-test.yml` висит только на `pull_request`, а в `release-0` мержат
напрямую. Расхождения скриншотов на React 17-сборке ловятся не здесь.

## Что проверяет предполёт

| Проверка | Что означает провал |
|---|---|
| `v1/<VERSION>.mdx` не заготовка | Выпускать нечего — штатный пропуск, не ошибка |
| Ни `1.Y.0`, ни `0.Y.0` не выпущены | Релиз уже был |
| Миноры `main` и `release-0` совпадают | Ветки разъехались по версиям |
| `main` влит в `release-0` | Перелитие не сделано или после него был коммит в `main` |
| CI на вершине `release-0` зелёный | Перелитие сломало ветку либо прогон не тот |

Ни одну из них workflow не «чинит» сам. Первая строка — единственный штатный
исход без релиза; остальные означают незавершённую подготовку, и прогон
напишет об этом в своём summary словами, с перечнем недостающих коммитов.

Смотреть результат: **Actions → Weekly release → последний прогон**. Если
предполёт не сошёлся, дальше все джобы будут `skipped` — это нормально,
ничего не опубликовано.

## Если предполёт отказал

**«Не хватает коммитов в `release-0`»** — в `main` что-то попало после
перелития, то есть заморозка была нарушена (или перелитие сделали до того,
как в `main` влили последнее). Долей `main` в `release-0` ещё раз, запушь,
дождись CI. Правки поверх мержа проверку не ломают — только новые коммиты
в `main`.

**«CI на `release-0` не зелёный»** — смотри прогон, чини в `release-0`.
Отдельными коммитами поверх мержа, это нормально.

**«Notes пустые»** — заполни `v1/<VERSION>.mdx` в `main`. Если `main` уже
заморожен, коммит с notes придётся перелить в `release-0` и заново получить
зелёный CI.

**«Прогон CI на другом коммите»** — после мержа что-то запушили в `release-0`
без ожидания CI. Дождись прогона на вершине ветки.

Во всех случаях не нужно ждать следующей пятницы: почини подготовку и
запусти **Actions → Weekly release → Run workflow** вручную. Там же есть
галка `dry_run` — прогнать только предполёт, ничего не публикуя.

## Если релиз выпущен наполовину

Теперь первой идёт `0.Y.0`, поэтому «половина» бывает двух видов, и они
сильно разной срочности.

### `0.Y.0` вышла, `1.Y.0` — нет. Это авария

`dist-tags.latest` остался на React 17-сборке, то есть
`npm install @sberbusiness/triplex-next` **отдаёт её всем потребителям**.
Ровно так и было с 31 июля по 7 августа, пока никто не замечал.

Чинить сразу, одним из двух способов:

```bash
# предпочтительно — довыпустить пару
/release-react18 VERSION=1.44.0 NEXT=1.45.0 V0=0.44.0 TASK=TRI-XXX

# если сейчас нельзя — вернуть тег на предыдущую React 18-версию
npm dist-tag add @sberbusiness/triplex-next@1.43.0 latest
```

Routine называет этот исход аварией первой строкой отчёта — не пропусти.

### `1.Y.0` вышла, `0.Y.0` — нет. Терпит

`latest` на месте, React 18-потребители получили новую версию. React
17-потребители остались на прежней — неприятно, но не ломает никого.

Доводится отдельно, версии нужно назвать явно:

```bash
/release-react17 V0=0.44.0 V1=1.44.0 NEXT0=0.45.0 TASK=TRI-XXX
```

Важно: после этого `latest` уедет на `0.44.0`, и вернуть его придётся руками
(`npm dist-tag add ...@1.44.0 latest`). Skill об этом предупредит.

## Ручной релиз

Автоматика — удобство, а не единственный путь. Если нужно выпустить релиз
не в пятницу или руками, локально:

```bash
/release 1.44.0
```

Запускать **локально** — из облачной сессии не сработает. Отличия от
автоматического: агент показывает diff и текст release notes и ждёт
подтверждения перед необратимыми шагами. Требования к веткам те же —
перелитие всё так же делается руками заранее.
