# Подготовка и выпуск релиза — гайд для разработчика

Этот документ — для людей. Он описывает, что нужно сделать с ветками `main`
и `release-0`, чтобы релиз выпустился сам по расписанию, и что делать,
когда она отказалась.

Машинные инструкции, по которым работает агент, живут в `.agents/skills/`
(`release-auto`, `release`, `release-react18`, `release-react17`) — этот файл
их не заменяет, а показывает процесс сверху.

---

## Как устроен релиз

Библиотека выпускается парами версий:

| Версия | Ветка | React | Порядок выпуска |
|---|---|---|---|
| `0.Y.0` | `release-0` | 17 | первая |
| `1.Y.0` | `main` | 18 | вторая |

`0.Y.0` — функциональный аналог `1.Y.0` с React 17-адаптациями. Минор у них
всегда общий.

**Порядок обратен номерам версий, и это важно.** Во внутренний npm registry
пакет попадает зеркалированием, а не `npm publish`: dist-tags туда
не проносятся, и `latest` определяется порядком появления версий. Поэтому `1.Y.0` выпускается второй —
только так `latest` остаётся на React 18-сборке, и
`npm install @sberbusiness/triplex-next` отдаёт именно её.

На npmjs теги работают, и с TRI-146 `0.Y.0` публикуется под тегом `react17`:
npm 11 отказывается неявно вешать `latest` на версию ниже уже опубликованной,
и прогон 18 сентября на этом упал. Там `latest` на React 17-сборку больше
не уезжает, а сама версия ставится и по тегу, и по точному номеру.

Публикацию в npm делает GitHub Actions (`release.yml`). Ни у кого локально
npm-токена нет и не нужно. Запускается он тремя способами:

- **по расписанию** — `release-weekly.yml` вызывает его дважды, для `0.Y.0`
  и `1.Y.0`. Это основной путь; перед каждой публикацией владелец кода
  одобряет соответствующий релизный PR: сначала в `release-0`, затем в `main`;
- **вручную человеком** — создаёшь GitHub Release, workflow срабатывает по
  событию `release: published`. Текст notes из MDX собирает
  `node scripts/releaseNotesMd.js <файл.mdx>`;
- **локальным агентом** — skill `release` делает то же самое пошагово.

Из облачной сессии Claude — **никак**: прокси запрещает и создание релизов,
и запуск workflow, и push тегов. Поэтому расписание держит сам GitHub, а не
routine.

Все пути ведут к одному и тому же: сборка, публикация, ассеты, деплой
Storybook. Обратная сторона: **опубликованную версию нельзя отозвать**,
поэтому все проверки стоят до этого момента.

### Что настроено один раз

Автоматический путь опирается на три настройки репозитория. Если релиз
внезапно останавливается после предполёта или перед публикацией — проверь
в первую очередь их.

| Настройка | Где | Зачем |
|---|---|---|
| Секрет `DUDIM_AI_GH_TOKEN` | Settings → Secrets and variables → Actions | PAT `dudim-ai` (`contents: write`, `pull-requests: write`) — под ним workflow пушит бамп версии и открывает релизный PR |
| `dudim-ai` и мейнтейнер в push restrictions, без bypass | Settings → Branches → правила для `main` и `release-0` | бот сливает релизный PR только после человеческого ревью; новые коммиты сбрасывают одобрение |
| Обязательные проверки на обеих ветках = имена джоб `ci.yml`, `visual-test.yml` и `deployment-security.yml` | Settings → Branches → правила для `main` и `release-0` | релизный PR требует зелёных проверок, актуальной базы (strict) и одобрения владельца кода |

Обе ветки принимают изменения только через PR, включая релизные коммиты.
Weekly release создаёт `prerelease-0.Y.0-run-<RUN_ID>-<ATTEMPT>` → `release-0`,
затем `prerelease-1.Y.0-run-<RUN_ID>-<ATTEMPT>` → `main`. Ручной выпуск
сохраняет имена `prerelease-0.Y.0` / `prerelease-1.Y.0`. Каждая повторная
подготовка получает новую ветку и PR; прежние ветки не перезаписываются. После проверок владелец кода одобряет PR;
workflow ждёт до часа и сам выполняет обычное слияние без обхода защиты.
Коммит слияния сверяется по содержимому с проверенной сборкой и передаётся
публикации. Новые коммиты сбрасывают одобрение. Если час истёк, одобрите PR
и повторите упавшие jobs. Пока React 17 PR не одобрен, ничего не публикуется;
ожидание React 18 начинается после публикации React 17.

`github-actions[bot]` в эти списки добавить нельзя — пикер показывает только
людей, команды и установленные GitHub Apps. Поэтому и нужен PAT машинного
аккаунта.

Имена семи обязательных проверок зафиксированы также в `scripts/release/open-pr.sh`:
workflow ждёт регистрации полного набора. При изменении защиты обновляйте
этот список. Открытие и слияние PR выполняются в отдельных чистых jobs со
скриптами из SHA workflow. Подготовка не запускает зависимости: build, unit,
visual и security остаются обязательными проверками самого релизного PR.

После любых изменений в этих настройках прогоняй **Actions → Weekly release
→ Run workflow** с галкой `dry_run`: выполнится только предполёт, ничего не
опубликуется.

Отдельно — публикация в npm. Она опирается на trusted publishing (OIDC)
и ломается иначе: релиз не останавливается, а **молча** уходит по запасному
токену без provenance. Видно это только в summary шага `Verify provenance`
после реальной публикации — `dry_run` до этого шага не доходит.

| Настройка | Где | Зачем |
|---|---|---|
| Trusted publisher `release.yml` | npmjs.com → пакет → Settings → Trusted Publisher (GitHub Actions, `SberBusiness/triplex-next`, environment пустой) | ручной релиз: `release: published` и `workflow_dispatch` у `release.yml`, в том числе через skill `release` |
| Trusted publisher `release-weekly.yml` | там же, отдельной записью | еженедельный релиз. npm сверяет имя **вызывающего** workflow: при `workflow_call` это `release-weekly.yml`, хотя publish выполняется в `release.yml`. Без этой записи так и вышли по токену `0.48.0` и `1.48.0` (TRI-152) |
| Секрет `NPM_AUTH_TOKEN` | Settings → Secrets and variables → Actions | запасной путь, если обмен OIDC не состоялся. Не удалять, пока обе записи выше не подтверждены публикацией с provenance: `npm view @sberbusiness/triplex-next@<версия> dist.attestations` не пусто |

## Кто что делает

Релиз целиком выпускает **GitHub Actions** — workflow
`release-weekly.yml` по расписанию GitHub. Claude в выпуске не участвует:
из облачной сессии релиз не выпустить, прокси режет создание релизов, push
тегов и запуск workflow. За ним остался отчёт.

| Когда | Кто | Что |
|---|---|---|
| весь спринт | **человек** | пункты в `stories/release-notes/v1/<VERSION>.mdx` |
| пт до 12:00 | **человек** | домержить задачи в `main`, дальше заморозка |
| пт ~12:00 | **человек** | PR синхронизации в `release-0`, конфликты React 17, проверки, ревью и merge commit |
| сразу после | GitHub | `ci.yml` на push в `release-0` |
| пт 13:23 | GitHub + **владелец кода** | предполёт → PR `0.Y.0`, одобрение, публикация → PR `1.Y.0`, одобрение, публикация |
| пт 13:45 | **человек** | прогона нет — запустить вручную (расписание опаздывает) |
| пт ~14:00 | Claude | резюме в Linear, отметка аномалий |

Твоя часть — подготовка, ревью PR синхронизации и двух релизных PR,
плюс проверка запуска в 13:45. Бот сливает одобренные релизные PR сам.
Notes пишутся по ходу спринта, заморозка — это просто «не мержить».

### Откуда GitHub знает, что релизить

Версию берёт из `main`: минор в `package.json` + 1. Стоит `1.43.0` — значит
выпускается `1.44.0`.

Признак «есть что релизить» — **заполненные release notes на эту версию**,
`stories/release-notes/v1/1.44.0.mdx`. Файл существует всегда: заготовку
создаёт предыдущий релиз, а пункты в неё дописываются по ходу спринта.
Смотрит workflow не на наличие файла, а на содержимое:

- только шапка (`import`, `<Meta>`, `<Title>`, пустые `<Heading>`) — выпускать
  нечего, прогон штатно выходит;
- есть хоть один пункт — релизим.

Отдельного переключателя «в эту пятницу не релизим» нет. Чтобы пропустить
неделю с непустыми notes — отключи workflow в Actions или не делай перелитие
(тогда предполёт откажет, но напишет об этом как об ошибке подготовки).

## Расписание и заморозка `main`

Прогон стартует **по пятницам в 13:23 МСК**. Вокруг него окно заморозки:

```text
12:00  начало заморозки: в main больше ничего не мержим
       ├─ PR синхронизации main → release-0, конфликты, ревью
       └─ зелёный CI на release-0
13:23  предполёт → PR 0.Y.0 → ревью → публикация → PR 1.Y.0 → ревью → публикация
13:45  прогона всё ещё нет — запускаем вручную
после завершения обеих публикаций — заморозка снята
```

Три уточнения, без которых окно не работает:

**Заморозка начинается не по часам, а до перелития.** 12:00 — плановая
граница, при которой перелитие делается после неё. Начнёшь мерж в 12:05,
а в 12:30 кто-то вольёт PR в `main` — предполёт откажет: `release-0` уже
не содержит вершину `main`. Правило простое: **перелитие всегда последнее,
что происходит с `main` перед релизом.**

**Заморозка снимается по завершении прогона, а не в 14:00.** Полчаса
с запасом — оценка, не гарантия: внутри установка зависимостей, unit-тесты,
сборка, две публикации в npm и деплой Storybook. Коммит, попавший в `main`
после предполёта, молча в `1.Y.0` уже не уедет: прогон сверяет содержимое
`main` с проверенным и собирает ровно проверенный коммит (TRI-155). Если
мерж пришёлся на первые минуты — до публикации `0.Y.0`, — прогон
остановится, ничего не выпустив: перелить заново и запустить снова. Если
позже — остановится на полпути (`0.Y.0` вышла, `1.Y.0` нет), и довести
релиз можно только откатом влитого (см. «Если релиз остановился на
проверках `1.Y.0`»). Мерж во время прогона стоит полдня разбирательств.

**Время — ориентир, а не гарантия.** Расписание GitHub Actions работает
best-effort: при высокой нагрузке прогон приходит на часы позже времени.
Опоздали оба состоявшихся плановых прогона: 28.08 — на 11 часов,
04.09 — на 4; минута в cron выбрана некруглой именно поэтому (на начале
часа очередь максимальная), но полностью проблему это не снимает.
**Если к 13:45 в Actions нет прогона `Weekly release` — запусти его
вручную**: Actions → Weekly release → Run workflow, галку `dry_run`
не ставь. Предполёт тот же самый, ничего лишнего ручной запуск не сделает.

Опоздавший плановый прогон потом всё равно придёт и штатно выйдет пустым
(«пустая заготовка notes» — версия уже забамплена ручным релизом). Это
нормально и ничего не ломает, но отчёт за неделю нужно читать по ручному
прогону, а не по нему.

**Если страховку не сделал — неделя, скорее всего, останется без релиза.**
Прогон придёт вечером, когда заморозка давно снята и в `main` уже приехали
новые коммиты, и упрётся в предполёт: `release-0` больше не содержит
вершину `main`. Выхода два — перелить `main` → `release-0` заново, дождаться
зелёного CI и запустить workflow вручную, либо перенести релиз на следующую
неделю. Первое лучше: несмерженная неделя копит расхождение веток.

**Нарушение заморозки видно сразу.** Workflow `release-freeze-guard.yml`
проверяет мержи в `main`: если перед мержем вершина `main` уже была
перелита в `release-0`, notes на кандидата заполнены, а релиз ещё не вышел —
мерж сорвал заморозку. Тогда в смерженный PR приходит комментарий
с упоминанием того, кто мержил, списком коммитов, которых не хватает
в `release-0`, и инструкцией. Действовать по ней, не дожидаясь отказа
предполёта: перелить `main` → `release-0` заново, дождаться зелёного CI
и, если плановый прогон уже отказал или не пришёл, запустить **Weekly
release** вручную. Сигнал приходит на первый мерж, сорвавший заморозку, —
следующие ничего не меняют: лечение то же. Окно определяется состоянием
веток, а не днём недели, поэтому вне него сигнал не срабатывает: после
релиза в `main` лежит бамп версии, которого в `release-0` нет. Релизный
коммит самого workflow сигналом не считается.

Частные случаи, которые комментарий различает сам:

- **мерж пришёлся в середину прогона** — `Weekly release` идёт прямо сейчас.
  В `1.Y.0` мерж не попадёт: прогон сверяет содержимое `main` с проверенным
  предполётом и остановится, выпустив только `0.Y.0` (TRI-155). Комментарий
  даёт ссылку на прогон: больше не мержить, сообщить ведущему релиз, после
  остановки — откатить мерж и нажать «Re-run failed jobs»;
- **релиз остановился на половине** — прогона нет, `0.Y.0` вышла, `1.Y.0`
  нет. Перелитие не поможет: новый прогон откажет, `0.Y.0` уже существует.
  Действовать по «Если релиз выпущен наполовину»;
- **перелитие было промежуточным** (синхронизация посреди недели) или релиз
  решили перенести — сигнал ожидаем: notes наполняются по ходу спринта,
  и предполёт без нового перелития всё равно откажет. Достаточно перелить
  перед релизом, как обычно.

Если релиз на этой неделе не планируется, заморозка не нужна вовсе.


## Чек-лист подготовки

Порядок важен. Пункт 3 выполняется **после** пунктов 1 и 2: коммит, попавший
в `main` после перелития, уронит проверку — и релиза не будет. Это касается
и правки release notes: она тоже коммит в `main`.

### `main`

**1. Смержить все задачи спринта.** Крайний срок — 12:00 пятницы, дальше
`main` заморожен до конца прогона. Заморозка не формальность: `release-0`
перелита из конкретного состояния `main`, и любой новый коммит делает её
устаревшей. Вторая причина — релизный коммит `1.Y.0` попадает в `main`
после проверки неизменности его базы: влитый во время прогона PR сдвигает
вершину и останавливает слияние релизного PR.

**2. Проверить release notes.** Файл `stories/release-notes/v1/<VERSION>.mdx`
должен быть заполнен — это шапка плюс реальные пункты:

```mdx
import { Meta, Title, Heading } from "@storybook/addon-docs/blocks";

<Meta title="release-notes/v1/1.44.0" />

<Title>v1.44.0</Title>

<Heading>Изменения</Heading>

- Badge: добавлена тема DANGER
```

Файл заводится заготовкой на предыдущем релизе, и пункты в него добавляются
по ходу спринта — обычно к пятнице он уже заполнен и делать ничего не нужно.
Голая шапка без пунктов = выпускать нечего, прогон штатно пропустит неделю.

Отдельного действия «объявить релиз» нет: заполненные notes и есть это
объявление.

### `release-0`

**3. Перелить `main`:**

```bash
git fetch origin main release-0
git switch -c sync-release-0-<дата> origin/release-0
git merge --no-commit --no-ff origin/main
```

`--no-commit` останавливает слияние перед коммитом, даже если конфликтов нет:
lock-файл и аудит из шага 4 должны войти в сам коммит слияния, а без флага
git закоммитил бы результат раньше проверок.

**4. Разрешить конфликты.** Общий принцип: из `main` берётся логика и
поведение, из `release-0` сохраняется React 17-совместимость.

| Что | Откуда брать |
|---|---|
| React-зависимости в `package.json` | всегда из `release-0` (`react` 17.0.2, `@testing-library/react` 12.1.5 и т.д.) |
| Остальное в `package.json` | из `main` |
| `package-lock.json` | из `main`, затем `npm install` и проверка аудита — см. ниже |
| `.github/workflows/release.yml` | из `main` |
| `stories/release-notes/v0/*` | из `release-0` |
| `src/**` | логика из `main`, типовые адаптации из `release-0` |

**Lock-файл: сторона `main` и проверка аудита.** Руками lock-файл не
разрешаем. Сначала разреши `package.json`, затем:

```bash
git checkout origin/main -- package-lock.json
npm install
npm audit --audit-level=high
```

Именно `origin/main --`, а не `--theirs`: `--theirs` выбирает сторону только
у файла с конфликтом. Если git слил `package-lock.json` сам, `--theirs` молча
оставит результат автослияния.

Почему из `main`, а не «любая сторона». В lock-файле `main` лежат исправления
вложенных зависимостей, которых нет в `package.json`: результат `npm audit fix`
и обновлений Dependabot. `npm install` при готовом lock-файле оставляет
зафиксированные версии как есть, поэтому сторона `release-0` эти исправления
теряет. Так и вышло 13.11.2026: после перелития `npm audit` показал
в `release-0` 47 находок, из них 10 high, при 34 без high в `main`.

Если `npm audit --audit-level=high` прошёл — проверка закончена. Если
завершился с ошибкой:

- запусти `npm audit fix` и повтори проверку; одного прохода бывает мало —
  повторяй, пока число находок не перестанет меняться;
- `--force` в `release-0` не используй: он поднимает мажорные версии и может
  сдвинуть React 17-зависимости.

Если ошибка осталась, выясни, чьи это находки — только `release-0` или общие
с `main`. Число находок для этого не годится: при том же количестве набор
может быть другим. Сравнивай по пакету и идентификатору advisory:

```bash
# Находки high и critical в виде «пакет идентификатор-advisory», по одной на строку.
# Завершается с ошибкой, если отчёт npm audit не получен или не разобран.
# Ненулевой код самого npm audit — не ошибка: так он сообщает о найденных уязвимостях.
audit_high() {
  npm audit --json "$@" | node -e '
    let s = "";
    process.stdin.on("data", (d) => (s += d)).on("end", () => {
      let report;
      try {
        report = JSON.parse(s);
      } catch {
        console.error("audit_high: отчёт npm audit не разобран");
        process.exit(1);
      }
      if (report.error || typeof report.vulnerabilities !== "object" || report.vulnerabilities === null) {
        console.error("audit_high: отчёт npm audit не получен:", JSON.stringify(report.error ?? {}));
        process.exit(1);
      }
      const found = new Set();
      for (const v of Object.values(report.vulnerabilities))
        for (const via of v.via)
          if (typeof via === "object" && ["high", "critical"].includes(via.severity))
            found.add(`${via.name} ${String(via.url ?? via.source).split("/").pop()}`);
      // Сортировка по кодам символов совпадает с LC_ALL=C — её ждёт comm ниже.
      process.stdout.write([...found].sort().map((line) => line + "\n").join(""));
    });'
}

BASE=$(mktemp -d)
git show origin/main:package.json > "$BASE/package.json"
git show origin/main:package-lock.json > "$BASE/package-lock.json"

if audit_high > /tmp/audit-release-0.txt &&
  (cd "$BASE" && audit_high --package-lock-only) > /tmp/audit-main.txt; then
  # Находки high и critical, которые есть в release-0 и которых нет в main.
  LC_ALL=C comm -13 /tmp/audit-main.txt /tmp/audit-release-0.txt
else
  echo "Отчёт npm audit не получен — перелитие не продолжать"
fi
```

Сначала смотри, нет ли сообщения «Отчёт npm audit не получен». Оно значит,
что сравнение не состоялось (нет сети, нет lock-файла, сбой реестра): его
повторяют, а не трактуют как «находок нет».

Критерий — оба отчёта получены и сравнение ничего не выводит: в `release-0`
нет high и critical сверх того, что есть в `main`.

- **Вывод пуст.** Оставшиеся находки общие с `main`: они чинятся там и
  приезжают следующим перелитием. Перелитие можно продолжать.
- **Вывод не пуст.** Каждая строка — находка, которая есть только
  в `release-0`. Вложенный пакет поднимается прицельно: `npm update <пакет>`.
  Если находка сидит в пакете, версия которого закреплена ради React 17
  (список — в таблице выше), в `main` её не починить: это решение мейнтейнера,
  `--force` здесь тоже не выход.

Находки уровня moderate и low в сравнение не входят.

Когда конфликты разрешены и аудит пройден, закоммить слияние:

```bash
git add package.json package-lock.json
git commit
```

`git add` здесь обязателен. `git checkout origin/main -- package-lock.json`
помечает файл как разрешённый, а `npm install`, `npm audit fix` и
`npm update` меняют его уже после этого. Без `git add` в коммит уйдёт
lock-файл `main` — с React 18, — а пересобранный останется незакоммиченным.
После коммита `git status` должен быть чистым.

Всё выше делается **до** этого коммита — по той же причине, что и в шаге 5:
зелёный прогон CI должен стоять на вершине `release-0`.

Полная карта известных расхождений (полиморфные типы, `React.JSX`, `Portal`,
тесты) — в `.agents/skills/release-react17/SKILL.md`, раздел «Что делает
человек до релиза». Там же — grep-проверка на React 18-only API
(`useId`, `createRoot`, `react-dom/client` и прочее). Она сравнивает
`origin/release-0` с `HEAD`, поэтому запускается после коммита слияния и
до пуша: до коммита диапазон пуст, и проверка ничего не найдёт.

**5. (Опционально) Release notes для React 17.** По умолчанию workflow
переносит текст `v1/1.44.0.mdx` → `v0/0.44.0.mdx` сам, меняя только
заголовки. Если какой-то пункт для React 17-сборки звучит иначе — заполни
`v0/0.44.0.mdx` руками и закоммить в `release-0`: заполненный файл workflow
не трогает.

Делай это **до** пуша, а не после. Routine проверяет, что зелёный прогон CI
стоит ровно на вершине `release-0`; коммит, добавленный после прогона,
сдвинет вершину, и проверка откажет. Если всё-таки закоммитил позже —
обнови PR синхронизации и дождись нового прогона.

**6. Открыть PR синхронизации в `release-0`.** Запушить только временную
ветку, создать PR с base `release-0`, дождаться всех обязательных проверок
(включая visual regression и безопасность) и одобрения владельца кода.
Слить через **Create a merge commit**. Squash и rebase не подходят:
предполёт проверяет `git merge-base --is-ancestor origin/main origin/release-0`.

После слияния `ci.yml` повторно запускается на push в `release-0` — именно
зелёный прогон на новой вершине проверяет предполёт. Красный CI чиним до релиза.
Если PR создал сам мейнтейнер, одобрение должен дать другой владелец кода;
автор не может одобрить собственный PR.

### Actions

**7. В 13:45 проверить, что прогон стартовал.** Расписание опаздывает
(см. «Расписание и заморозка `main`»). Прогона в Actions нет — запусти
**Weekly release → Run workflow** сам, без галки `dry_run`.

---

## Что проверяет предполёт

| Проверка | Что означает провал |
|---|---|
| `v1/<VERSION>.mdx` не заготовка | Выпускать нечего — штатный пропуск, не ошибка |
| Ни `1.Y.0`, ни `0.Y.0` не выпущены | Релиз уже был |
| Миноры `main` и `release-0` совпадают | Ветки разъехались по версиям |
| `main` влит в `release-0` | Перелитие не сделано или после него был коммит в `main` |
| CI на вершине `release-0` зелёный | Перелитие сломало ветку либо прогон не тот |

Ни одну из них workflow не «чинит» сам. Первая строка — единственный штатный
исход без релиза; остальные означают незавершённую подготовку, и прогон
напишет об этом в своём summary словами, с перечнем недостающих коммитов.

Смотреть результат: **Actions → Weekly release → последний прогон**. Если
предполёт не сошёлся, дальше все джобы будут `skipped` — это нормально,
ничего не опубликовано. Оговорка: если релиз выпускался вручную, самым
последним в списке окажется опоздавший плановый прогон — пустой. Результат
недели смотри по тому прогону, который реально публиковал.

---

## Если предполёт отказал

**«Не хватает коммитов в `release-0`»** — в `main` что-то попало после
перелития, то есть заморозка была нарушена (или перелитие сделали до того,
как в `main` влили последнее). Повтори PR синхронизации `main` → `release-0`, слей его после ревью,
дождись CI. Правки поверх мержа проверку не ломают — только новые коммиты
в `main`. Если заморозку сорвал мерж PR, об этом уже написал
`release-freeze-guard.yml` в самом PR.

**«CI на `release-0` не зелёный»** — смотри прогон, чини в `release-0`.
Отдельными коммитами поверх мержа, это нормально.

**«Notes пустые»** — заполни `v1/<VERSION>.mdx` в `main`. Если `main` уже
заморожен, коммит с notes придётся перелить в `release-0` и заново получить
зелёный CI.

**«Прогон CI на другом коммите»** — после мержа что-то запушили в `release-0`
без ожидания CI. Дождись прогона на вершине ветки.

**«release-0 изменился после предполёта»** или **«main изменился после
предполёта»** на шаге `prepare-react17` — это уже не предполёт: он прошёл,
а до сборки `0.Y.0` в `release-0` что-то запушили или в `main` что-то влили.
Собирается ровно проверенное состояние (TRI-155), поэтому прогон
остановился — ничего не опубликовано. Для `release-0` — дождись зелёного CI
на новой вершине, для `main` — перелей заново, затем запусти прогон снова
(или «Re-run all jobs»; «Re-run failed jobs» не подойдёт — предполёт должен
проверить новое состояние).

Во всех случаях не нужно ждать следующей пятницы: почини подготовку и
запусти **Actions → Weekly release → Run workflow** вручную. Там же есть
галка `dry_run` — прогнать только предполёт, ничего не публикуя.

## Если релиз остановился на проверках `1.Y.0`

Релизный коммит React 18-половины едет в `main` не напрямую: он уходит
в ветку `prerelease-<VERSION>-run-<RUN_ID>-<ATTEMPT>`, на её PR идут обязательные проверки,
и после одобрения владельца кода выполняется слияние в `main`. Если проверка
упала или ожидание проверки/ревью вышло за час, прогон останавливается **до** публикации
`1.Y.0`. Но `0.Y.0` к этому моменту уже вышла — половины идут в обратном
порядке, — так что это релиз, выпущенный наполовину, и чинить его нужно
в тот же день (см. ниже).

Если упала только джоба `finalize-react18` и причина не в изменившейся
`main` до слияния, «Re-run failed jobs» повторяет завершение с теми же PR
и SHA: уже выполненное слияние распознаётся, дерево проверяется повторно,
новый бамп версии не создаётся. Если упала подготовка
`prepare-react18`, повторяется подготовка в новой ветке и новый PR требует ревью.
Если упала `open-react18`, повторяется открытие/ожидание для прежнего SHA;
уже слитый PR распознаётся без создания второго.

Ветка и PR при этом остаются намеренно: в них лежит релизный коммит
и результаты проверок, по которым разбирают причину. Прогон пишет об этом
в summary.

Что делать:

- **почини причину и повтори нужную джобу** — при ошибке подготовки
  `prepare-react18` создаст новую ветку и PR для этой попытки, при ошибке завершения
  `finalize-react18` повторит слияние и проверку прежнего SHA. Если сдвинулась
  `main` до слияния, действуй по инструкции ниже. Новый запуск целиком
  не подойдёт: предполёт откажет, `0.Y.0` уже существует;
- **если выпуск решено отменить, а PR ещё открыт** — закрой PR без слияния;
  временную ветку можно удалить после проверки её текущих коммитов. Вопрос
  `latest` во внутреннем registry решается по разделу «`0.Y.0` вышла, `1.Y.0` — нет»;
- **если PR уже слит** — ветка не является способом отмены: бамп уже в `main`.
  Штатный путь — продолжить failed jobs исходного прогона с прежним SHA.
  Отмена требует отдельного решения мейнтейнера: подтвердить отсутствие версии
  в npm и GitHub Releases, восстановить прежнюю версию и notes через проверенный
  revert-PR, сохранив прочие изменения main, и решить состояние внутреннего
  `latest`. До этого новый Weekly release не запускать. Если версия уже в npm,
  откатом ветки публикацию не отменить — довести текущий выпуск до конца.

Откат бампа лишь останавливает текущую попытку: `0.Y.0` уже опубликована,
а `main` после отката имеет `1.(Y-1).0`. Разные миноры блокируют новый Weekly
release даже после восстановления `latest`. Для возврата к расписанию нужно
довыпустить парную `1.Y.0` из согласованного состава изменений, вернуть `main`
на `1.Y.0` через проверенный PR и проверить обе публикации/теги и CI веток.
Версии `main` и `release-0` снова должны иметь одинаковый минор, а `latest`
указывать на React 18. Поэтому предпочтительно не откатывать бамп, а завершить
исходный выпуск; одного revert-PR недостаточно для восстановления расписания.

**Если прогон остановился на «main изменился после предполёта».** После
публикации `0.Y.0` прогон сверяет содержимое `main` с тем, что проверил
предполёт: если в `main` что-то влили, `1.Y.0` собралась бы вместе с этим
и разошлась бы с `0.Y.0` (TRI-155). Выход, при котором версии остаются
точной парой, — откатить влитое в `main` (revert), повторить подготовку,
а изменения вернуть после выхода `1.Y.0`. На этапе подготовки сверяется
содержимое, поэтому откат проходит эту проверку.

**Если `main` сдвинулась после подготовки, пока PR ждал проверок или ревью.**
Шаг слияния требует, чтобы текущая вершина `main` была родителем подготовленного
коммита. Revert восстанавливает файлы, но создаёт новый SHA, поэтому повтор
только `finalize-react18` снова остановится. После восстановления содержимого
`main` перезапусти именно **`prepare-react18` вместе с зависимыми jobs**, даже
если она была зелёной: в исходном прогоне выбери эту джобу → **Re-run jobs**
(через CLI: `gh run rerun <RUN_ID> --job <PREPARE_JOB_ID>`). Подготовка создаст
релизный коммит на новой вершине `main`; после проверок потребуется новое ревью.
«Re-run failed jobs» в этом случае недостаточно.

**Если ошибка случилась после успешного слияния**, повторяй только упавшие
jobs: `finalize-react18` распознает слитый PR. Подготовку заново не запускай.

**Если React 18 PR закрыт без слияния, но выпуск нужно продолжить.**
Если вершина `main` осталась той же, на которой готовился PR, перезапусти
`prepare-react18` исходного прогона вместе с зависимыми jobs (команда выше).
Новая попытка получит другую ветку и новый PR, проверки и ревью нужны заново.
Повтор только failed jobs найдёт прежний закрытый PR и снова остановится.
Если `main` изменился, сначала восстанови состав изменений по инструкции выше.
Для открытого PR с исходным SHA и неизменной базой достаточно failed jobs.

Нужно одобрить релизный PR. Слияние выполнит workflow с соблюдением защиты ветки.

## Если остановился React 17 PR до публикации

В `prepare-react17` готовится коммит, `open-react17` создаёт PR
`prerelease-0.Y.0-run-<RUN_ID>-<ATTEMPT>` → `release-0` и ждёт полный набор проверок;
`finalize-react17` ждёт одобрения владельца кода. Пока этот этап не завершён,
ни одна половина не опубликована. PR остаётся для диагностики; временная
ветка после слияния может быть автоматически удалена GitHub.

- **Истекло ожидание ревью, база не менялась:** одобрить PR и выполнить
  «Re-run failed jobs». Новый бамп не нужен.
- **Изменилась база PR или main, React 17 PR ещё не слит:** закрыть устаревший
  PR и проверить `git merge-base --is-ancestor origin/main origin/release-0`
  после fetch. Если main уже в истории release-0, новая синхронизация не нужна:
  дождаться зелёного CI на её вершине и запустить новый Weekly release.
  Если main не хватает — сначала PR синхронизации с сохранением React 17.
  Старый прогон не продолжать: он хранит прежние SHA предполёта.
- **PR уже слит, но публикация не началась:** не запускать новый предполёт
  и не повторять бамп — версии веток пока различаются. Если main не менялся,
  повторить failed jobs: и `open-react17`, и финализатор распознают слитый PR
  по прежней ветке и подготовленному SHA. Открытие не создаст второй PR,
  финализатор повторно проверит дерево, ancestry и заморозку main.
  Если main изменился, вернуть его содержимое к SHA предполёта через revert-PR,
  затем повторить failed jobs старого прогона. После обеих публикаций вернуть
  изменения обычным PR. Это же правило действует, если main сдвинулся прямо
  во время слияния React 17 PR.

При **ручном** выпуске исходного Weekly release может не быть. Если PR уже
слит, продолжить шаг публикации `release-react17` с ранее проверенного merge
SHA через `release.yml` (`workflow_dispatch`, входы `tag=<V0>` той же попытки, `target=release-0`,
`sha=<MERGED_SHA>`, `make_latest=false`), повторно сверив дерево и `main`
с сохранённым SHA предполёта. Не начинать
новый предполёт/бамп. Если сохранённый SHA недоступен, остановиться; подставлять
текущую вершину `main` нельзя.

## Если проверка публикации остановила выпуск

Повторный выпуск сверяет `gitHead` уже опубликованной npm-версии с SHA
checkout. Только совпадение позволяет пропустить npm publish и продолжить
создание Release, ассетов и Storybook. Другой или отсутствующий `gitHead`
останавливает прогон: возобновляйте исходный выпуск с подтверждённым SHA,
а не создавайте тег на новом коммите. При отсутствии метаданных нужна ручная
проверка происхождения пакета; автоматический пропуск запрещён. Ошибка
чтения реестра тоже останавливает прогон, а не означает отсутствие версии.

До публикации через workflow_dispatch/workflow_call сравниваются
`.github/workflows/` у checkout и основной ветки: при различии `GITHUB_TOKEN`
не имеет права создать Release. Не расширяйте права токена для обхода этой
проверки. Сверьте, какие workflow вошли в подготовку, и исправьте синхронизацию
через PR, выбрав восстановление по фактическому этапу выпуска (разделы выше).
Если версия уже опубликована, нельзя заменять её исходный SHA новым; при
невозможности восстановить согласованное состояние остановитесь для решения
мейнтейнера. Заморозка main действует до завершения обеих половин: проверка
файлов перед публикацией не блокирует дальнейшие изменения ветки на GitHub.

## Если релизный PR слит через squash/rebase

Финализатор требует исходный подготовленный SHA в истории merge-коммита.
При squash/rebase он останавливается до публикации с явным сообщением;
перезапуск не исправит историю и новый бамп делать нельзя. Для релизных PR
используйте **Create a merge commit** (сам workflow выбирает этот метод).

Восстановление — отдельное решение мейнтейнера. По исходному PR подтвердите
подготовленный head SHA, его зелёные проверки и одобрение; при удалённой ветке
получите объект через `refs/pull/<PR>/head` и сверьте SHA. Сравните полные
деревья подготовленного и фактического merge SHA, проверьте принадлежность
merge SHA целевой ветке, соответствие версии и состояние тегов/публикаций.
Для React 17 также требуется совпадение main с сохранённым предполётом.
Если хотя бы одно условие не подтверждено — остановитесь. При подтверждении
мейнтейнер может продолжить публикацию точного merge SHA через `release.yml`
с `tag`, `target`, `sha` и соответствующим `make_latest` (false для 0.x,
true для 1.x), соблюдая порядок 0.x → 1.x. Затем проверьте обе половины
и согласованность версий по разделу восстановления частичного выпуска.

Проверка заморозки и `npm publish` не являются одной атомарной операцией.
После проверки в финализаторе `main` ещё может измениться, в том числе во
время сборки публикации. Поэтому запрет на новые мержи действует до завершения
обеих публикаций. Если правило нарушено, React 17 может успеть выйти, а
React 18 остановится: восстановление выбирается по фактическому статусу ниже.

## Если релиз выпущен наполовину

Теперь первой идёт `0.Y.0`, поэтому «половина» бывает двух видов, и они
сильно разной срочности.

### `0.Y.0` вышла, `1.Y.0` — нет. Это авария

Во внутреннем registry `latest` считается по последней публикации и остался
на React 17-сборке, то есть `npm install @sberbusiness/triplex-next`
**отдаёт её всем потребителям**. Ровно так и было с 31 июля по 7 августа,
пока никто не замечал. На npmjs с TRI-146 этого уже не происходит: `0.Y.0`
уходит под тегом `react17`, `latest` остаётся на прежней `1.x`.

Чинить сразу. Сначала — «Re-run failed jobs» упавшего прогона, если
причина понятна и устранена (см. «Если релиз остановился на проверках
`1.Y.0`»). Если так не выходит — одним из двух способов:

```bash
# предпочтительно — довыпустить пару
/release-react18 VERSION=1.44.0 NEXT=1.45.0 V0=0.44.0 TASK=TRI-XXX

# если сейчас нельзя — вернуть тег на предыдущую React 18-версию
npm dist-tag add @sberbusiness/triplex-next@1.43.0 latest
```

Routine называет этот исход аварией первой строкой отчёта — не пропусти.

### `1.Y.0` вышла, `0.Y.0` — нет. Терпит

`latest` на месте, React 18-потребители получили новую версию. React
17-потребители остались на прежней — неприятно, но не ломает никого.

Доводится отдельно, версии нужно назвать явно:

```bash
/release-react17 V0=0.44.0 V1=1.44.0 NEXT0=0.45.0 TASK=TRI-XXX
```

Важно: во внутреннем registry `latest` после этого уедет на `0.44.0` — он
считается по последней публикации. На npmjs всё остаётся на месте: `0.44.0`
публикуется под тегом `react17`, и править `dist-tags` руками не нужно.
Skill об этом предупредит.

## Ручной релиз

Автоматика — удобство, а не единственный путь. Если нужно выпустить релиз
не в пятницу или руками, локально:

```bash
/release 1.44.0
```

Запускать **локально** — из облачной сессии не сработает. Отличия от
автоматического: агент показывает diff и текст release notes и ждёт
подтверждения перед необратимыми шагами. Требования к веткам те же —
перелитие всё так же делается руками заранее.
