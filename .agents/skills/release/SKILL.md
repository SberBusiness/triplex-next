# release

Оркестратор релиза. Выпускает обе версии библиотеки строго по очереди:

```text
1. 0.Y.0  →  release-react17   (ветка release-0, React 17)
2. 1.Y.0  →  release-react18   (ветка main,      React 18)
```

**Порядок обратен номерам версий, и менять его нельзя.** Теги не проносятся
во внутренний npm registry — `--tag` при публикации игнорируется, и
`dist-tags.latest` всегда встаёт на последнюю опубликованную версию. Поэтому
`1.Y.0` выпускается второй: только так `latest` остаётся на React 18-сборке.

MCP-сервер `@sberbusiness/triplex-next-mcp-server` обновляется **не отсюда**:
его репозиторий сам следит за релизами библиотеки (workflow `sync-bundle.yml`
по расписанию) и выпускается собственным skill'ом `release`. Со стороны
triplex-next достаточно, чтобы в релиз попал ассет `mcp-data-<версия>.json` —
его кладёт шаг `Generate MCP bundle` в
[`release.yml`](../../../.github/workflows/release.yml).

Сам ничего не коммитит и не публикует — вся механика в под-скиллах. Его
работа: проверить входные данные, запустить под-скиллы по очереди, не дать
второму стартовать при провале первого и собрать общий итог.

## Когда запускать

По явной просьбе выпустить релиз с указанием версии, либо из
[`release-auto`](../release-auto/SKILL.md) — еженедельной routine, которая
сама делает предполётные проверки и передаёт сюда версию.

При ручном запуске версия — обязательный аргумент: если её нет и запуск
не из `release-auto`, спроси, не угадывай.

Нужна только одна половина — вызывай соответствующий под-skill напрямую:
[`release-react18`](../release-react18/SKILL.md) или
[`release-react17`](../release-react17/SKILL.md).

## Входные данные

- `VERSION` — React 18-версия, формат `1.Y.0`. Выпускаются только минорные
  релизы: `Y` = текущий минор + 1, патч всегда `0`.
- `V0` — `0.Y.0`, парная React 17-версия; минор совпадает с `VERSION`.
- `NEXT` — `1.(Y+1).0`, для заготовки release notes React 18-половины.
- `NEXT0` — `0.(Y+1).0`, то же для React 17-половины.
- `TASK` — номер задачи Linear на релиз, формат `TRI-XXX`. Используется
  префиксом в релизных коммитах обеих половин. Если разработчик не назвал
  задачу и подходящей нет — заведи её через skill `create-task` («Релиз
  <VERSION>») до запуска под-скиллов, чтобы обе половины использовали
  один номер.

- `UNATTENDED` — признак запуска из routine, без человека у клавиатуры.
  По умолчанию `false`; передаётся в обе половины как есть.
- `PUBLISH_MODE` — режим публикации в unattended: `full` (право на диспатч
  `release.yml` подтверждено зондом [`release-auto`](../release-auto/SKILL.md))
  или `prepare` (по умолчанию; облако). Передаётся в обе половины как есть;
  в интерактивном режиме не используется.

Разработчик может назвать любую из двух версий («выпусти 1.40.0» / «выпусти
0.40.0») — вторая выводится из минора. Если названы обе и миноры не
совпадают — остановись и спроси.

**Если версия не передана** — выведи её из `origin/main`: `VERSION` — минор
текущей версии + 1, патч `0`. Так приходит запуск из `release-auto`, но
правило общее: разработчик тоже может сказать просто «выпусти релиз».

```bash
git fetch origin main
git show origin/main:package.json | grep -m1 '"version"'
git show origin/main:stories/release-notes/v1/<VERSION>.mdx
```

Последняя команда — чтобы сразу увидеть, есть ли что выпускать: непустые
notes проверяются на шаге 1.

`1.40.0` в `main` → выпускается `1.41.0`. Читай именно из `origin/main`, а не
из рабочей копии: чекаут может стоять на произвольной ветке.

## 1. Предварительная проверка

Один общий взгляд до запуска под-скиллов, чтобы не выпустить `1.Y.0` и
только потом обнаружить, что вторая половина невозможна:

```bash
git status --porcelain
git fetch origin main release-0
git show origin/main:package.json | grep -m1 '"version"'
git show origin/release-0:package.json | grep -m1 '"version"'
gh release view <VERSION> 2>&1 | head -3
gh release view <V0> 2>&1 | head -3
git merge-base --is-ancestor origin/main origin/release-0
```

Проверки — при провале остановись и сообщи разработчику:

- Рабочее дерево чистое (исключение — заготовки release notes, созданные
  вручную).
- Ни `VERSION`, ни `V0` ещё не выпущены.
- Минор в `main` и в `release-0` совпадает — ветки не разъехались по версиям.
- `stories/release-notes/v1/<VERSION>.mdx` существует и **не пустой** по
  предикату заготовки из [`release-react18`](../release-react18/SKILL.md),
  шаг 1 — иначе публиковать нечего, релиза нет.
- Перелитие `main` → `release-0` уже сделано человеком: `is-ancestor`
  проходит. При провале покажи недостающие коммиты
  (`git log origin/main --not origin/release-0 --oneline`) и остановись —
  доливать main самостоятельно нельзя.

`is-ancestor` сверяется с вершиной `origin/main` напрямую: React 17-половина
идёт первой, до того как релизный PR React 18 добавит в `main` коммит с
бампом. Никаких зафиксированных SHA передавать между скилами не нужно.

## 2. React 17 — `release-react17`

**Порядок половин обратный по отношению к номерам версий, и это намеренно.**
Теги не проносятся во внутренний npm registry: `--tag` при публикации
игнорируется, и `latest` всегда встаёт на последнюю опубликованную версию.
Значит порядок выпуска — единственное, что управляет `latest`. Выпустив
`0.Y.0` первой, а `1.Y.0` следом, мы оставляем `latest` на React 18-сборке.
Обратный порядок 31 июля привёл к тому, что `npm install` неделю отдавал
всем React 17-версию.

Запусти [`release-react17`](../release-react17/SKILL.md), передав все
объявленные им входы:

| Вход | Значение |
|---|---|
| `V0` | `0.Y.0` — минор из `VERSION` |
| `V1` | `VERSION` — только для переноса notes из `v1/<V1>.mdx` |
| `NEXT0` | `0.(Y+1).0` |
| `TASK` | номер задачи Linear на релиз |
| `UNATTENDED` | как передано сюда |
| `PUBLISH_MODE` | как передано сюда |

Он проверит готовность `release-0` (перелитие сделано человеком, CI зелёный),
прогонит локальные гейты, перенесёт notes из `v1/<V1>.mdx` и выпустит `0.Y.0`.
Публикации `1.Y.0` он **не требует** — нужен только сам файл notes, который
пишется по ходу спринта и попадает в `release-0` перелитием.

Перелитие `main` → `release-0` он не делает — оно должно быть выполнено до
запуска релиза.

**Гейт.** Если под-skill остановился — остановись и ты, но помни: если
`0.Y.0` уже опубликована, а `1.Y.0` нет, `latest` завис на React 17-сборке
(см. «Если половина не вышла»).

**Unattended при `PUBLISH_MODE=prepare` — остановка на публикации, и это
штатный исход, а не провал.** Из облака публиковать нельзя ни одним путём
(прокси сессий запрещает `gh release create`, `gh workflow run release.yml`,
`repository_dispatch` и push тегов — зонд TRI-117, 2026-08-14), поэтому
`release-react17` доводит подготовку до точки невозврата и останавливается
с готовой командой. React 18-половину в этом случае **не запускай**: её
гейт «`V0` опубликована» заведомо не пройдёт. Итоговый отчёт — «релиз
подготовлен, публикацию завершает человек» с командой из отчёта
`release-react17` и указанием продолжить локально React 18-половиной.
`latest` при таком исходе не тронут — аварии нет.

При `PUBLISH_MODE=full` (право на диспатч подтверждено зондом) unattended
проходит обе половины целиком: публикация идёт через
`gh workflow run release.yml` внутри под-скилов.

Покажи разработчику итог первой половины; в unattended — включи его в
итоговый отчёт.

## 3. React 18 — `release-react18`

Запусти [`release-react18`](../release-react18/SKILL.md), передав все
объявленные им входы:

| Вход | Значение |
|---|---|
| `VERSION` | `1.Y.0` |
| `NEXT` | `1.(Y+1).0` |
| `V0` | `0.Y.0` — для гейта «пара уже опубликована» |
| `TASK` | тот же номер задачи, что и в React 17-части |
| `UNATTENDED` | как передано сюда |
| `PUBLISH_MODE` | как передано сюда |

Передавать нужно все пятеро: без `TASK` под-skill полезет заводить задачу
через `create-task`, без `UNATTENDED` — уйдёт в `gh pr checks --watch` и
станет ждать подтверждения, которого в routine некому дать.

Он ведёт весь цикл: ветка `prerelease-<VERSION>` → бамп → PR → зелёный CI →
мерж → GitHub Release → публикация в npm, после которой `latest` встаёт на
`1.Y.0`.

## Если половина не вышла

Обратный порядок создаёт состояние, которого при прежнем не было: **`0.Y.0`
опубликована, `1.Y.0` — нет.** Тогда `dist-tags.latest` указывает на React
17-сборку, и `npm install @sberbusiness/triplex-next` отдаёт её всем
потребителям.

Это авария, а не «релиз наполовину». В отчёте она должна стоять первой
строкой и явно называться, а не прятаться среди прочих итогов. Чинится
одним из двух способов:

- довыпустить `1.Y.0` — [`release-react18`](../release-react18/SKILL.md)
  отдельным запуском (предпочтительно: потребители получают то, что должны);
- если это невозможно прямо сейчас — вернуть тег вручную:
  `npm dist-tag add @sberbusiness/triplex-next@<предыдущая 1.x> latest`.

Обратная ситуация («`1.Y.0` вышла, `0.Y.0` нет») безобидна для `latest`:
React 17-потребители просто остаются на прежней версии.

## 4. Проверить ассет для MCP-сервера

После публикации `1.Y.0` убедись, что в релизе есть ассет с бандлом
AI-документации:

```bash
gh release view <VERSION> --json assets --jq '.assets[].name'
```

Ожидается `mcp-data-<VERSION>.json` рядом с `dist-<VERSION>.zip`. Если его
нет — шаг `Generate MCP bundle` не отработал; сообщи разработчику, потому что
MCP-сервер не сможет синхронизироваться.

Ничего больше делать не нужно: репозиторий mcp-server сам подхватит релиз
своим workflow `sync-bundle.yml` и откроет PR с обновлённым bundle.

## 5. Общий итог

Собери в одном сообщении:

- `0.Y.0`: ссылка на GitHub Release, результат гейтов, каким путём пошли
  release notes;
- `1.Y.0`: ссылка на PR и на GitHub Release;
- **`dist-tags.latest` = `1.Y.0`** — единственная проверка тегов, которая
  имеет смысл. `dist-tags.react17` не поддерживается: теги не проносятся
  в внутренний registry, и на нём висит давняя версия. Не проверяй его и не
  пытайся починить;
- наличие ассета `mcp-data-<VERSION>.json` в релизе;
- пути к созданным заготовкам notes (`1.(Y+1).0.mdx`, `0.(Y+1).0.mdx`);
- ссылки на Storybook обоих релизов.

Если какая-то часть не выпущена — скажи это явно и назови причину.

## Преобразование MDX → release notes

Общий канон для обоих под-скиллов. Текст для GitHub Release получается из
`.mdx` механическим преобразованием:

| В MDX | В release notes |
|---|---|
| строка `import { ... } from "@storybook/addon-docs/blocks";` | удалить |
| `<Meta title="..." />` | удалить |
| `<Title>vX.Y.Z</Title>` | удалить |
| `<Heading>Текст</Heading>` | `## Текст` |
| всё остальное | без изменений |

Подряд идущие пустые строки схлопни в одну; убери пустые строки в начале
файла. Результат положи во временный файл в скретчпаде — **не** в репозиторий.

Исполняемая форма канона —
[`scripts/releaseNotesMd.js`](../../../scripts/releaseNotesMd.js):
`node scripts/releaseNotesMd.js <файл.mdx>` печатает готовый markdown в
stdout. Предпочитай его ручному преобразованию — он сверен с notes
выпущенного релиза 1.42.0 (совпадение с точностью до хвостового перевода
строки).

Готовый текст покажи разработчику перед созданием релиза.

## Жёсткие ограничения

- Не запускать без версии: либо она передана явно, либо однозначно выводится
  из версии в `origin/main` (минор + 1).
- Не мержить `main` в `release-0` — это ручной шаг мейнтейнера.
- Не менять порядок половин: сначала `0.Y.0`, потом `1.Y.0`. От него зависит,
  на чём останется `dist-tags.latest`.
- Не запускать React 18-часть, если React 17-часть не дошла до подтверждённой
  публикации в npm.
- Не оставлять `latest` на `0.x`: если `1.Y.0` не вышла, это авария —
  см. «Если половина не вышла».
- Не лезть в репозиторий mcp-server: он синхронизируется сам, а его релиз —
  задача его собственного skill'а.
- Не подменять шаги под-скиллов «своими» командами — вся механика релиза
  живёт в них, здесь только последовательность и гейты.
