# update-visual-baselines

Приводит `__screenshots__/` в соответствие с текущими stories ветки:
свежие baseline из CI + удаление orphan-файлов. Локально на macOS
скриншоты не генерируются никогда (рендеринг шрифтов отличается от Linux).

## Предусловия

- Ветка запушена на origin — workflow работает с веткой на GitHub.
  Если есть незапушенные коммиты — сначала запушь (в задаче Linear это
  часть автоматического финала, вне её — спроси пользователя).
- `gh` авторизован (`gh auth status`).
- Рабочее дерево чистое (workflow добавит коммит, который нужно будет
  подтянуть без конфликтов).

## Воркфлоу

### 1. Определи, нужен ли прогон

Посмотри diff ветки (`git diff main...HEAD --stat`). Прогон нужен, если:

- добавлены/переименованы/удалены stories (`stories/**`) — меняется набор
  story ID, а имена скриншотов строятся из них;
- менялся визуал компонента (LESS, разметка) при существующих baseline.

Если ничего из этого не менялось — сообщи «прогон не нужен» и выйди.

### 2. Запусти прогон маркерным коммитом и дождись

Прогон запускается **пушем**, а не диспатчем: из облачной сессии
`gh workflow run` отдаёт 403 «Resource not accessible by integration»
(см. `docs/ai/commits.md` § «Облачные сессии»). Триггер — маркер
`[update-snapshots]` в сообщении HEAD-коммита ветки `TRI-*`/`TRIPLEX-*`.

Работы уже закоммичены, поэтому маркер везём пустым коммитом:

```bash
if [ -n "$TRIPLEX_BOT_GH_TOKEN" ]; then export GH_TOKEN="$TRIPLEX_BOT_GH_TOKEN"; fi
git commit --allow-empty -m "TRI-XXX Обновление baseline-скриншотов [update-snapshots]"
git push
```

Дальше ищем свой прогон и ждём:

```bash
sleep 10   # run появляется в списке не мгновенно
# Бери run именно этого запуска — фильтруй по headSha текущего HEAD,
# слепой --limit 1 может зафиксировать более старый run этой ветки.
gh run list --workflow=visual-update.yml --branch <ветка> --limit 5 \
  --json databaseId,headSha \
  -q '[.[] | select(.headSha == "'"$(git rev-parse HEAD)"'")][0].databaseId'
gh run watch <run-id> --exit-status --interval 30
```

Если фильтр вернул пусто — run ещё не зарегистрировался, подожди ещё
10–20 секунд и повтори `gh run list`.

Ручной путь через `gh workflow run visual-update.yml --ref <ветка>`
сохранён и работает из локальной сессии — в облачной он недоступен.

**Маркер ищется во всём сообщении коммита**, не только в заголовке. Поэтому
не упоминай `[update-snapshots]` и `[skip ci]` в телах других коммитов —
сработает как настоящий маркер (см. `docs/ai/commits.md` § «Формат
коммитов»).

**Пока идёт прогон — не пушь в ветку.** Workflow делает `git pull --rebase`
перед своим пушем, но лишняя гонка ни к чему; новые коммиты копи локально
и пушь после завершения. Не прячь код возврата `gh run watch` за pipe
(`| tail` вернёт свой exit code) — проверяй статус run'а отдельно.

Прогон обычно занимает 5–15 минут. Если упал — `gh run view <run-id>
--log-failed`, покажи причину пользователю. Один повторный запуск допустим
при инфраструктурной ошибке (сеть, таймаут установки браузера); при
падении самих визуальных тестов — не перезапускай, разбирайся.

### 3. Подтяни результат

```bash
git pull --ff-only
```

`--ff-only` защищает от незаметного merge-коммита: если история
разошлась (кто-то запушил в ветку во время прогона) — команда упадёт;
остановись и разберись, не создавай merge/rebase автоматически.

Workflow коммитит `chore: update visual snapshots` только если скриншоты
изменились. «No snapshot changes» в логе — не ошибка.

Коммит пушится под PAT бота и без `[skip ci]` — значит на нём запускаются
CI и визуальные проверки. Это обязательное свойство: на `main` проверки
обязательные, и PR с вершиной без прогонов смержить нельзя.

### 4. Найди и удали orphan-скриншоты

Имя baseline: `{story-id}--{viewport}.png`, где `story-id` — ID story из
Storybook-индекса (например `textfields-textfield--sizes`), viewport —
`xs`/`xl`. Workflow обновляет и добавляет файлы, но не удаляет
скриншоты исчезнувших story — это делаем здесь.

1. Возьми актуальный список story ID: `npm run storybook:build` и прочитай
   `storybook-static/index.json` (если storybook-static уже собран на этой
   ревизии — используй его).
2. Для каждого `__screenshots__/*.png` (каталог `__diff__` пропусти) отрежь
   суффикс `--{viewport}.png` и проверь, есть ли такой story ID в индексе.
3. Файлы без соответствующей story удали через `git rm`, коммит по
   конвенциям ветки (например `TRI-XXX Удалить orphan-скриншоты
   переименованных stories`), пуш. Pre-commit hook пропускает удаления в
   `__screenshots__/` без подтверждения — вопрос задаётся только при
   добавлении/изменении скриншотов.

### 5. Проверь и отчитайся

- Убедись, что на PR перезапустился/пройдёт workflow «Visual Tests»
  (`gh run list --workflow=visual-test.yml --branch <ветка> --limit 1`).
- Отчёт пользователю: сколько baseline обновлено / добавлено / удалено
  (orphan), ссылка на run, статус Visual Tests.

## Жёсткие ограничения

- Не генерируй и не коммить скриншоты локально (macOS). Только CI.
- Не используй `HUSKY=0` / `--no-verify` — это привилегия CI-workflow.
- Удаляй только файлы, чей story ID отсутствует в актуальном
  `storybook-static/index.json`. Сомневаешься — покажи список и спроси.
- Не запускай workflow повторно более одного раза без разбора причины.
- Не запускай на чужой ветке (не относящейся к текущей задаче).
