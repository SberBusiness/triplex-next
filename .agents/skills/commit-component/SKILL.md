# commit-component

Делает коммит текущих изменений по конвенциям `docs/ai/commits.md`.

## Когда запускать

Два легитимных сценария:

1. **Пользователь явно попросил коммитить.**
2. **Автоматически в финале работы по задаче Linear** — ветка `TRI-XXX-...`
   взята через skill `take-task`, работа завершена, `change-reviewer` дал
   зелёный свет (см. `docs/ai/commits.md` § «Когда коммитить и пушить»).
   В этом сценарии после коммита сразу пуш и создание PR (шаг 8).

Вне этих сценариев не запускайся: в memory пользователя есть правило
«не создавать коммиты без запроса». Если есть малейшее сомнение — спроси.

## Воркфлоу

### 1. Проверка состояния

Запусти параллельно:
```bash
git status              # без -uall — на больших репах ест память
git diff                # текущие unstaged изменения
git diff --staged       # staged изменения
git log -5 --oneline    # стиль последних коммитов
git rev-parse --abbrev-ref HEAD   # текущая ветка
```

Имя ветки должно быть в формате `TRI-XXX-краткое-описание` (см. `docs/ai/commits.md`; legacy-ветки — `TRIPLEX-XXX-...`). Извлеки номер задачи по паттерну `(TRI|TRIPLEX)-\d+` — он идёт в префикс коммита.

### 2. Анализ изменений

Раздели изменения на категории:
- Затронутые компоненты (`src/components/{Name}/...`)
- Stories (`stories/...`)
- Тесты (`src/components/{Name}/__tests__/...`)
- Документация (`docs/ai/...`, `*-ai.md`, release notes)
- Конфиги (eslint, vitest, storybook, ci)

Определи характер:
- **Add** — новый компонент / новый prop / новая story
- **Update** — изменение существующего поведения
- **Fix** — багфикс
- **Refactor** — рефакторинг без изменения публичного API (типичный AI refactoring)
- **Docs** — только документация / AI.md / release notes

### 3. Release notes — обязательная проверка

**Это шаг-гейт: не переходи к коммиту, не ответив на вопрос про release notes.**

Определи, менялось ли **публичное поведение** компонента. Release notes нужны не только при breaking change, а при **любом** изменении публичного API или наблюдаемого поведения (см. раздел «Release notes» в `docs/ai/commits.md`):

- новый или удалённый prop, изменение типа/значения по умолчанию;
- изменение того, что компонент рендерит или как себя ведёт при тех же props
  (например, автоматический `rel="noopener"` для `target="_blank"`, смена уровня
  логирования, изменение фокуса/клавиатуры/overlay-поведения);
- багфикс, который меняет наблюдаемое поведение.

Release notes **не нужны** для изменений только в stories / тестах / документации и для рефакторинга без изменения публичного API.

**Если release notes нужны:**
1. Найди текущую версию: `ls stories/release-notes/v1/` — бери файл с наибольшей версией (или уточни у пользователя, если готовится новая версия).
2. Убедись, что запись уже добавлена в `stories/release-notes/v1/<версия>.mdx` в формате из `docs/ai/commits.md` (компоненты — в алфавитном порядке; breaking change — в секцию «Ломающие изменения»).
3. Если записи нет — **останови коммит и сообщи пользователю**, предложи добавить release notes. Не коммить изменение публичного поведения без release notes.
4. Файл release notes должен попасть в тот же коммит, что и изменение компонента.

Если сомневаешься, публичное ли это изменение — **спроси пользователя**, а не пропускай.

### 4. Проверка безопасности

**Никогда не коммить:**
- `__screenshots__/*.png` если изменения локальные (macOS) — pre-commit hook должен заблокировать, но проверь сам.
- `.env*` файлы.
- `node_modules/`, `dist/`, `storybook-static/` — должны быть в `.gitignore`.
- Случайно сгенерированные временные файлы (`*.log`, `tmp.*`, IDE-specific).

Если в `git status` видишь подозрительный файл — **спроси пользователя**, не добавляй автоматически. Если файл не должен трекаться — предложи добавить в `.gitignore`.

### 5. Формат сообщения

```text
TRI-XXX Краткое описание (≤72 символа)
```

Если нужно уточнение — двоеточие:
```text
TRI-XXX Component: уточнение
```

Примеры:
```text
TRI-12 Добавить компонент Badge с темами и размерами
TRI-15 Button: исправить стиль фокуса в теме Link
TRI-21 List: AI refactoring + unit-тесты на ListItem
TRI-21 List: добавить List-ai.md и Storybook examples
```

Для legacy-веток `TRIPLEX-XXX-...` префикс остаётся `TRIPLEX-XXX`.

**Правила:**
- Первая строка ≤72 символов.
- Тело — опционально, для сложных изменений.
- Язык — русский **или** английский, не смешивать.
- Фокус — на «что» и «почему», не на «как».
- Не добавляй `Co-Authored-By: Claude` для этого проекта (в `docs/ai/commits.md` не предусмотрено).

### 6. Стейджинг и коммит

```bash
git add <конкретные файлы>     # не git add -A / git add .
git commit -m "TRI-XXX ..."
```

**Никогда не используй:**
- `git add -A` или `git add .` — может добавить sensitive/temp файлы.
- `--no-verify` — обходит linter/husky, нарушает требования проекта.
- `--amend` без явной просьбы пользователя.

### 7. Pre-commit hook

`husky` + `lint-staged` запустят `eslint --fix` и `prettier --write` на staged-файлах автоматически. Если упало:
1. Прочитай ошибку — это **не автофиксимое** ESLint-нарушение.
2. **Не используй `--no-verify`.** Исправь руками.
3. Пере-stage: `git add <files>`.
4. Создай **новый** коммит (не amend — амендить значит переписать предыдущий, который при упавшем хуке не создался; но если коммит был частично создан, амендить может потерять работу).

### 8. После коммита

```bash
git status   # подтверди успех
git log -1 --oneline
```

Покажи пользователю:
- Хеш коммита и одну строку сообщения.
- Что попало в коммит (список файлов).

**В автоматическом сценарии задачи Linear** (см. «Когда запускать») сразу
продолжи без подтверждения:

```bash
git push -u origin TRI-XXX-...
gh pr create --title "TRI-XXX Краткое описание" --body "..."
```

Покажи пользователю ссылку на PR и предложи `/finish-task`.

**Во всех остальных случаях не пушь автоматически.** Push и PR — только
по отдельной явной просьбе.

## Жёсткие ограничения

- **Не запускай вне двух сценариев из «Когда запускать»** (явная просьба
  пользователя либо финал задачи Linear после зелёного ревью).
- **Не коммить, если есть несохранённые/неотревьюенные изменения**, о которых пользователь может не знать. Если файлов в `git status` больше, чем ожидалось — сначала спроси.
- **Не коммить, если упали проверки** (tsc errors, failing tests). Сначала чини, потом коммит.
- **Не коммить изменение публичного поведения без release notes** (см. шаг 3). Если запись в `stories/release-notes/v1/<версия>.mdx` отсутствует — остановись и сообщи пользователю.
- **Не делай несколько коммитов** за один запуск без подтверждения. Один запуск = один коммит, если иное не оговорено.
- **Не пушь и не создавай PR вне автоматического сценария задачи Linear.** В остальных случаях push — отдельный шаг по отдельной просьбе.

## Если что-то странное в `git status`

Не пытайся «привести в порядок» автоматически. Покажи `git status` пользователю и спроси, как поступить:

- Незнакомые untracked файлы — может быть work-in-progress, который пользователь не закончил.
- Изменения в файлах, которые не имеют отношения к задаче — могут быть случайными правками.
- Состояние rebase/merge in progress — не вмешивайся, сообщи пользователю.

## Что включает «один коммит»

Связные изменения по одной задаче. Для типичной Phase 1 итерации по компоненту — это:
- Правки в `src/components/{Name}/`
- Тесты в `src/components/{Name}/__tests__/`
- Stories в `stories/.../{Name}/`
- `src/components/{Name}/{Name}-ai.md`
- Обновление `docs/ai/ROADMAP.md` (галочки)
- При изменении публичного поведения (не только breaking change) — `stories/release-notes/v1/<версия>.mdx` (см. шаг 3)

Всё это укладывается в один коммит `TRIPLEX-XXX {Name}: AI-Ready` или аналогичный.
