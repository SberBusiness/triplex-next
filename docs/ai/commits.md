# Коммиты и ветки — Triplex-Next

---

## Задачи и тикеты

Задачи ведутся в Linear, команда `TRI` (https://linear.app/triplex-next).
Номер задачи `TRI-XXX` — обязательный префикс веток и коммитов: по нему
GitHub-интеграция Linear линкует PR и двигает статусы задачи
(ветка → In Progress, PR → In Review, merge → Done).

**Legacy:** исторические ветки и коммиты используют префикс `TRIPLEX-XXX`.
Существующие не переименовываем; всё новое — только `TRI-XXX`.

---

## Именование веток

**Формат:** `TRI-XXX-короткое-описание`

- Строчные буквы, слова через дефис.
- Всегда начинается с номера задачи Linear.

```text
TRI-12-add-badge-component
TRI-15-fix-button-focus-style
TRI-21-alert-ai-ready
```

**Исключения:**
- Релизная ветка: `prerelease-X.Y.Z` (например, `prerelease-1.40.0`) — в неё
  собираются фиксы релиза и бамп версии, PR идёт в `main`
- Перелитие main → release-0: выполняется человеком без отдельной ветки,
  прямым мержем

Исключение касается только **имени ветки**. Коммиты внутри неё подчиняются
общему правилу `TRI-XXX`: на релиз заводится задача Linear, её номер идёт
префиксом (`TRI-XXX Подготовка релиза 1.40.0`). Legacy-префикс `TRIPLEX-0`
для новых релизов не используется.

---

## Структура веток и релизов

| Ветка | React | Версии пакета | Описание |
|---|---|---|---|
| `main` | React 18 | `1.xx` | Основная ветка разработки |
| `release-0` | React 17 | `0.xx` | Поддержка React 17, синхронизируется с main |

**Правило:** все фича-ветки создаются от `main`. Изменения попадают в `release-0` через перелитие. Агент не должен создавать ветки от `release-0` и не должен мерджить в неё напрямую.

**Перелитие делает человек, не агент.** Мерж `main` → `release-0` идёт
напрямую, без PR, с разрешением конфликтов React 17-адаптаций — это ручной
шаг мейнтейнера в конце спринта. Правила разрешения конфликтов и регламент
подготовки описаны в `.agents/skills/release-react17/SKILL.md` и
`docs/human/release.md`. Прямой push в `release-0` проверяется CI:
`ci.yml` триггерится на `push: branches: [release-0]`.

**Единственное исключение для агента** — релизный коммит `release-react17`
(бамп версии + release notes): он тоже пушится в `release-0` напрямую, без
PR. Прогон CI на него стартует, но дождаться его нельзя — GitHub Release
создаётся сразу после push. Поэтому исключение компенсируется обязательными
локальными гейтами (`tsc`, `test-unit`, `build`).

## Формат коммитов

**Формат:** `TRI-XXX Краткое описание`

```text
TRI-12 Добавить компонент Badge с темами и размерами
TRI-15 Исправить стиль фокуса для Button в теме Link
```

Если нужно уточнение — добавляй через двоеточие:

```text
TRI-12 Badge: добавить тему DANGER и размер SM
TRI-21 Alert: AI refactoring + unit-тесты
```

**Правила:**
- Все коммиты в ветке начинаются с одного номера задачи.
- Первая строка — не длиннее 72 символов.
- Тело коммита опционально (для сложных изменений).
- Язык: русский или английский — не смешивать в одном коммите.

## Когда запускать линтер

**Вручную запускать не нужно.** Линтер запускается автоматически при `git commit`:

1. `husky` перехватывает коммит.
2. `lint-staged` запускает на staged-файлах:
   - `eslint --fix` — автоисправление ESLint-ошибок
   - `prettier --write` — форматирование кода
3. Исправленные файлы добавляются обратно в staging.

**Если `lint-staged` упал:**
- Прочитай ошибку — это ESLint-нарушение, которое нельзя автофиксировать.
- Исправь вручную.
- Пере-stage: `git add <files>`.
- Повтори коммит.

**Ручной запуск (если нужно проверить до коммита):**
```bash
npx eslint --fix src/components/Button/Button.tsx
npx prettier --write src/components/Button/Button.tsx
```

## Что не коммитить

| Файл/папка | Причина |
|---|---|
| `__screenshots__/` | Только из Docker/CI. Если нужно — подтвердить в pre-commit hook |
| `.env.local` | Секреты — в `.gitignore` |
| `node_modules/`, `dist/`, `storybook-static/` | В `.gitignore` |

Если в ходе работы появились новые локальные, временные, генерируемые или
машино-специфичные файлы:
- проверь `git status`, не попали ли они в untracked/staged
- если такие файлы не должны храниться в репозитории, добавь подходящее правило в `.gitignore`
- не коммить подобные файлы "на всякий случай"

## Когда коммитить и пушить

**Вне задачи Linear агент не создаёт коммиты и не пушит самостоятельно.**
После завершения работы — остановиться и показать результат разработчику.
Коммит и пуш — только по явной просьбе.

**Исключение — работа по задаче Linear.** Если работа ведётся в ветке задачи
`TRI-XXX-...` (взятой через skill `take-task`), агент после завершения работ
и зелёного ревью (`change-reviewer`) **без подтверждения**:

1. делает коммит по конвенциям этого файла (skill `commit-component`);
2. пушит ветку;
3. дожидается PR от workflow `auto-pr.yml` (см. «PR-воркфлоу»; сам
   `gh pr create` в ветках `TRI-*` не вызывает);
4. если менялись stories или визуал компонентов — обновляет baseline-скриншоты
   через skill `update-visual-baselines` (CI-workflow «Update Visual
   Snapshots» + чистка orphan-скриншотов);
5. запускает skill `finish-task` — комментарий-резюме публикуется в задачу
   без подтверждения, проверяется линковка PR;
6. запускает агента `pr-reviewer` — независимое ревью PR «с чистого листа»
   с комментариями в GitHub (только COMMENT, вердикт и мерж за человеком).

Гейты остаются обязательными и в автоматическом режиме — при любом из них
остановиться и спросить разработчика:

- упавшие проверки (tsc / vitest / eslint);
- изменение публичного поведения без записи в release notes;
- блокеры от `change-reviewer`;
- подозрительные/посторонние файлы в `git status`.

## GitHub-операции от аккаунта бота

Автоматические GitHub-операции (комментарии в PR, запуск workflow,
авторство коммитов автофинала) выполняются от отдельного machine-аккаунта,
если у разработчика задан его токен:

```bash
# fine-grained PAT бота: contents:write, pull-requests:write, actions:write
export TRIPLEX_BOT_GH_TOKEN=...   # в ~/.zshenv (не ~/.zshrc — агент работает
                                  # в неинтерактивном shell), НЕ в репозитории
```

Тот же PAT хранится как repository secret `DUDIM_AI_GH_TOKEN` — его
использует workflow `auto-pr.yml`, который создаёт PR для веток `TRI-*`
(см. «PR-воркфлоу»). Благодаря этому автор PR один и тот же независимо от
того, где шла сессия агента — локально или в облаке. При ротации PAT
обнови оба места: `~/.zshenv` и secret
(`gh secret set DUDIM_AI_GH_TOKEN --body "$TRIPLEX_BOT_GH_TOKEN"`).

**Паттерн для агентов** — в начале Bash-вызова с командами `gh`:

```bash
if [ -n "$TRIPLEX_BOT_GH_TOKEN" ]; then export GH_TOKEN="$TRIPLEX_BOT_GH_TOKEN"; fi
gh pr comment ...  # выполнится от бота; без токена — от разработчика (fallback)
```

**Авторство коммитов автофинала** (identity бота выводится из токена,
дополнительные переменные не нужны):

```bash
if [ -n "$TRIPLEX_BOT_GH_TOKEN" ]; then
  BOT_LOGIN=$(GH_TOKEN="$TRIPLEX_BOT_GH_TOKEN" gh api user -q .login)
  BOT_EMAIL=$(GH_TOKEN="$TRIPLEX_BOT_GH_TOKEN" gh api user -q '"\(.id)+\(.login)@users.noreply.github.com"')
  git -c user.name="$BOT_LOGIN" -c user.email="$BOT_EMAIL" commit -m "..."
else
  git commit -m "..."
fi
```

Правила:

- Токен нигде не печатать, не логировать и не коммитить; в репозитории
  он не хранится ни в каком виде.
- `git push` остаётся по SSH разработчика — авторство коммита и аккаунт
  пушащего могут различаться, это нормально.
- Проверка «кто я» перед автофиналом: `gh api user -q .login`
  (с учётом паттерна выше) — чтобы в отчёте было видно, от чьего имени
  созданы PR/комментарии.
- Действия в Linear выполняются от сессии разработчика — бот на них
  не распространяется.

### Облачные сессии: подмена токена прокси

В облачных сессиях (routines на claude.ai) запросы к `api.github.com`
идут **не** с `TRIPLEX_BOT_GH_TOKEN`: egress-прокси подменяет авторизацию
на токен GitHub App `claude` (user-to-server, identity — аккаунт
разработчика). Паттерн выше при этом не ломается — просто действующие
права определяет прокси, а не PAT. Как распознать:

- `gh api user` возвращает аккаунт разработчика, хотя в env лежит токен
  бота;
- текст 403 — «Resource not accessible by **integration**» или «not
  permitted for this session type / through this proxy» (у fine-grained
  PAT было бы «…by personal access token»).

Что прокси **разрешает** из облака: push в ветки, создание и мерж PR,
комментарии, чтение Actions, диспатч нерелизных workflow (например,
`visual-update.yml` — подтверждено прогонами). Что **запрещает** (зонд
TRI-117, 2026-08-14): создание релизов, диспатч `release.yml`,
`repository_dispatch`, создание, push и удаление тегов, удаление веток —
блокируется публикация релизов любым маршрутом. Поэтому публикация релизов из
облака невозможна — облачный прогон готовит релиз и передаёт публикацию
человеку (см. `.agents/skills/release-auto/SKILL.md`). Диагностический
зонд права на диспатч: POST на
`actions/workflows/release.yml/dispatches` с несуществующим `ref` —
`422 No ref found` означает «право есть», `403` — «нет».

## PR-воркфлоу

**Работа по задаче Linear:** PR для веток `TRI-*` создаёт workflow
`auto-pr.yml` (триггер `on: push`) от аккаунта бота — secret
`DUDIM_AI_GH_TOKEN`. Так автор PR не зависит от среды сессии: локальный
`gh pr create` шёл бы от PAT бота, а облачный — от GitHub App `claude`
(прокси подменяет авторизацию, см. «Облачные сессии»). Агент **не вызывает
`gh pr create` в ветках `TRI-*`** — иначе облачная сессия успеет создать
PR от `claude[bot]` раньше workflow.

Финальный коммит — это и есть источник PR: заголовок берётся из первой
строки (`TRI-XXX Краткое описание`), описание — из тела коммита. Поэтому
в автофинале тело коммита обязательно и содержит описание PR
(«Что сделано» / «Как проверить»).

```bash
git push -u origin TRI-XXX-feature-name
# PR создаст auto-pr.yml через ~20–60 с; дождись его появления:
for i in $(seq 1 12); do
  pr_url=$(gh pr list --head "TRI-XXX-feature-name" --base main --state open \
    --json url --jq '.[0].url // empty') && [ -n "$pr_url" ] && break
  sleep 10
done
echo "${pr_url:-PR не появился}"
```

Если PR не появился за ~2 минуты — проверь прогон workflow именно для
текущего коммита (не по ветке: `--limit 1` по ветке может показать прогон
предыдущего пуша):
`gh run list --workflow=auto-pr.yml --commit $(git rev-parse HEAD) --limit 1`.
Дальше по статусу:

- `queued` / `in_progress` — прогон ещё идёт, продолжай ждать;
- `completed` + `success` без PR — сработал guard (маркер `[no-pr]`,
  subject не по формату `TRI-XXX ...` или ветка без новых коммитов
  относительно `main`) — штатное завершение без PR, fallback не нужен;
- `completed` + `failure` или прогона нет (например, протух secret) —
  fallback.
Fallback — прежняя схема: `gh pr create` с паттерном bot-токена из
раздела выше.
Fallback безопасен: раз workflow PR не создал, гонки нет. В облачной
сессии fallback-PR будет от `claude[bot]` (прокси подменит PAT — см.
«Облачные сессии») — это осознанная деградация, лучше PR от app'а, чем
отсутствие PR.

Обход автосоздания (WIP-пуш ветки `TRI-*` без PR): добавь маркер `[no-pr]`
в первую строку HEAD-коммита. Коммиты не по формату `TRI-XXX ...`
(например, `chore: ...`) PR также не создают.

После появления PR финал продолжается автоматически: skill
`update-visual-baselines` (если менялись stories/визуал) и skill
`finish-task` — комментарий-резюме в задаче Linear и проверка линковки PR
(GitHub-интеграция Linear подхватит PR по `TRI-XXX` в имени ветки).

**Вне задачи Linear:** агент пушит ветку и создаёт PR только по явной просьбе
разработчика; по умолчанию PR открывает разработчик через GitHub UI или
`gh pr create`.

## Release notes

При добавлении или изменении публичного поведения компонента — обнови файл release notes текущей версии:

```
stories/release-notes/v1/<текущая версия>.mdx
```

**Что писать:**

- Новый prop: «Добавлено свойство `X` для ...»
- Изменение поведения: «Изменён/Исправлен ...»
- Удалённый prop (breaking change): выноси в секцию `<Heading>Ломающие изменения</Heading>`

**Формат записи:**

```mdx
**ComponentName**

- Добавлено свойство `propName` для описания.
```

Компоненты внутри секции — в алфавитном порядке.

### Главное правило: пиши только то, что стало новым для потребителя

Release notes читает потребитель библиотеки, а не разработчик репозитория.
Запись отвечает на один вопрос: **что изменилось для того, кто подключает
компонент**. Всё остальное — лишнее.

**Не попадает в release notes:**

- внутренняя кухня репозитория: количество unit-тестов, созданные `*-ai.md`,
  обновлённые stories и `ROADMAP.md`, JSDoc, переименования внутренних констант,
  порядок импортов, чистка LESS;
- перечисление того, что **не** изменилось: списки прежних props, значений
  enum'ов, barrel-экспортов, границ диапазонов. Если поведение не изменилось,
  достаточно сказать это одной фразой — без инвентаризации;
- обоснования и подробности реализации, интересные только ревьюеру. Им место
  в описании PR и в `{Component}-ai.md`.

**Рефакторинг без изменений для потребителя — одна короткая строка:**

```mdx
**ComponentName**

- Проведён AI-рефакторинг.
```

Если рефакторинг всё же дал потребителю что-то наблюдаемое (например
`displayName`, видимый в React DevTools) — назови только это:

```mdx
**MediaWidth**

- Проведён AI-рефакторинг, добавлен `displayName`.
```

Ориентир по объёму: запись про изменение поведения — 1–3 предложения, запись
про рефакторинг — одна строка. Если запись разрослась до абзаца, скорее всего
в неё попала внутренняя кухня — вычеркни её.

Не нужно добавлять release notes для изменений только в stories, тестах или
документации.

## Чек-лист перед пушем

- [ ] Линтер проходит (автоматически при коммите)
- [ ] Unit-тесты проходят: `npm run test-unit`
- [ ] Нет случайно добавленных файлов (`git status`)
- [ ] Для новых локальных/временных/генерируемых файлов проверено, не нужно ли добавить правило в `.gitignore`
- [ ] Нет скриншотов из macOS в `__screenshots__/`
- [ ] Release notes обновлены (если изменился публичный API **или наблюдаемое поведение** компонента — не только при breaking change)
